## 2. What stops the slice

**S19-A. The object store: a dependency and a local service, neither of which the repository has.**

- Production is DigitalOcean Spaces in FRA1, which speaks the S3 protocol. Reaching it needs a client. Plan row C18 names "The AWS S3 client (Apache-2.0)", to be reviewed under NFR-IC-12 "in the slice that adds each"; the rules of this task forbid adding a dependency without stopping. It would be two packages, pinned exactly: `@aws-sdk/client-s3` (put, delete, head) and `@aws-sdk/s3-request-presigner` (the 5-minute link).
- Development needs a local equivalent that issues and checks signed links. `compose.yaml` says "The object store for images joins this file with the slice that first uses it". None is set up on this machine: no `minio`, no other S3-compatible server on a port, no `node_modules/@aws-sdk`. CI would need it as a third service, and `ci-local.mjs` would need it started (it must not be changed from here).
- The link is the reason a file-system adapter is not enough. NFR-SE-18 has the link served by the storage, signed and expiring, and "not a request path of the application". A file adapter would have to serve the bytes from a route of the application that carries no session, which NFR-SE-05 forbids, even for development only: that route would be the one path the requirements say does not exist, and the tests of expiry and of scope would test it and not the real thing.

What I would add, for the owner to decide: **MinIO** (`minio/minio`) in `compose.yaml` on 9000, with a bucket created at start by the `mc` client image, the two AWS packages, the five settings of section 5, and in `ci.yml` a step that runs the same container (a GitHub `services:` entry cannot be given the `server /data` command) and waits for its health check; and in `ci-local.mjs` the same. Alternatives in row S19-1.

**S19-B. A domico gap: the resize handle.** FR-ED-08 requires resizing "via a drag handle". `@ekdotico/domico` 0.31.0 has `Figure` (an `img` and a caption), `TextField`, `TextArea`, `Select`, `Button`, `Toolbar` and `Dialog`, and in `styles/editor.css` a handle of its own for a table column (`.ekd-column-resize`), but no image block in "The document surface" contract and no handle for the width of a block. Nothing here may be improvised. The closest existing thing is `.ekd-column-resize`; the recommendation is the first of the three the package's rule 4 allows, extending that pattern: a `.ekd-image-resize` handle and an `.ekd-image` block (selected, unavailable and uploading states) in the next release. WCAG 2.2 2.5.7 (Dragging Movements) also asks for a way to set the width without dragging; that part is built from existing controls (a `Select` of widths in the block's own controls, `BlockControls`), and is not blocked.

The rest of the block's controls are the package's: the picker is a `Button` that opens a hidden `<input type="file" accept="image/png,image/jpeg,image/gif,image/webp">` (a native element, not a control that is drawn); alt text and caption are `TextField`s; the statements are `FormFault`s with the announce setting the others use. The layout of the block is a rule of `editor.module.css` made from tokens, as the table's is.

## 3. What is built when the owner answers (nothing here waits on either)

**Storage interface** (`src/lib/images/storage.ts`): `put(key, bytes, contentType)`, `remove(key)` (answers whether the object existed; removing one that is gone is not a fault), `link(key, seconds, contentType)` (a signed URL for `GET`, no other method), and the one function that makes a key. Two adapters: the S3 one, for Spaces and for MinIO, chosen by the settings; and an in-memory one for the unit tests only. A key is `images/<documentId>/<32 random hex>`, from `crypto.randomBytes(16)`: it names its document (NFR-SE-18), it cannot be guessed, and nothing a user typed is in it, not the file name, which no route reads. A user's file name is not accepted at all.

**Data model**: the Data models page's `DocumentImage` as drawn (`id`, `documentId`, `objectKey` unique, `contentType`, `byteSize`, `uploadedById`, `createdAt`, `unreferencedAt`), and one column that page does not have, `deletionClaimedAt`, the claim of the timer, in the manner of `Document.deletionClaimedAt` (reported; section 7). One migration. `@@index([documentId])`; the foreign key restricts: the permanent deletion removes the rows before the document's. Held as `ekdotico_app` under the usual privileges; the migration role creates it.

**Server-side checks of the shared document** (`src/lib/collab/shape.ts`; the unit tests of `collab-shape.test.ts`): a new node `image` (a block, no content, an atom) in `NODES`, the same in `extensions.tsx`, and a test that the two agree (the test exists). An update that creates or changes an element named `image` is refused (as the other shape results are) where it carries an attribute that is not `id`, `alt`, `caption`, `width`; where `id` is not of the form the application issues (a cuid: 25 characters of a to z and 0 to 9, starting with `c`); where `alt` or `caption` is longer than its bound or `width` is not a whole number in its bounds (row S19-3). "An address" cannot be held: any `src`, `href`, `url`, or `data` attribute is outside the list. The block counts as one block in the total of 5,000 (`ONE_BLOCK`): an addition to D192, row S19-6. What the server does not do: look up the `id` in the database on every update, which would put a query on the path of every keystroke; a block whose `id` names no image of this document shows the statement that the image is not available, and the link route says 404 (IDOR is closed there, section 5).

**The reference, and the clock of the timer** (`src/lib/images/references.ts`, called from the store in `src/lib/collab/state.ts`): when the collaboration server stores a document it reads the `id`s of the `image` elements from the Yjs document it holds, compares with the set it kept from the last store, and only where they differ writes: `unreferencedAt = now()` for rows of this document that are no longer in the set (and have none), `unreferencedAt = null` for rows that are in it. A row that is claimed for deletion is not revived (Q14: "an image that reappears before its deletion is kept"; the claim is the moment of deletion). A new row starts with `unreferencedAt = createdAt`: an image uploaded and never placed is deleted 30 days later like one taken out. The first store after a start writes whatever differs, so the set that is lost in a restart is found again.

**The timer** `image-deletion` in `TIMERS` (`src/lib/images/deletion.ts`; hourly, at start; says how many images it deleted). One run: (1) claims, with one conditional `UPDATE … WHERE unreferencedAt <= now − 30 days AND (deletionClaimedAt IS NULL OR deletionClaimedAt < now − 1 hour)`, the rows due, returning them; (2) for each, removes the object (a missing object is success); (3) deletes the row where its `deletionClaimedAt` is still the claim it made. A run that fails after the claim is taken up again by the run that finds the claim an hour old; a run on a second instance claims nothing that the first has claimed, or finds the object gone and the row gone, and says 0. The permanent deletion of a document (`deletePermanently`) removes the objects of all its rows, then the rows and the document in the transaction it already has; an object that cannot be removed keeps the document (the existing outcome `kept`, retried).

**The 100 MB** (Q14, every stored object counts): in the upload, in one transaction under `pg_advisory_xact_lock(hashtext('images:' || documentId))`, the sum of `byteSize` of the document's rows plus the new image is compared with 100 MB (`IMAGE_DOCUMENT_MEGABYTES`, an initial value, 100, a megabyte of 1,024 × 1,024 bytes as the 5 MB of `state.ts` and the 500 KB of the code block are counted) and the row is inserted in the same transaction: two uploads at once cannot both pass it.

### 4.1 Removing the metadata (Q13), without compressing the image again

Whitelist, never blacklist: the container is read to its end and a new one is written from the parts that are known to be needed; every other part, known as metadata or not, is dropped. The pixel data are copied byte for byte. The unit tests have one file for each kind of metadata that exists in each format, and read the result back: the kind is gone, and the pixels (and, for the formats that carry them, the frames) are the same bytes.

The orientation of a photograph is in its Exif block: removing the block turns many phone photographs on their side, because the browser then shows the pixels as stored. That is the sharpest consequence of the removal and is row S19-2.

## 5. The 5-minute link

`GET /api/documents/[id]/images/[imageId]`, as the API design page has it, made by `documentRoute('document.view', …, { row: true })`. The option makes the route read the session's row by `validateSessionRow` and never the cookie cache, and a test requires it of this route (`tests/unit/routes.test.ts` gains a list of the routes that issue a link or take the export, as `READS_A_DOCUMENT` is held now). The handler looks the image up by `{ id: imageId, documentId: document.id }` (so an image of another document, however the caller got its `id`, is a 404 for this document, byte for byte the 404 of an `id` that does not exist: IDOR across documents), checks that the row is not claimed for deletion, and answers `200 { "url", "expiresAt" }` with `Cache-Control: no-store`: a signed `GET` of the object's key, valid for 300 seconds (`IMAGE_LINK_SECONDS`, an initial value), with `response-content-type` the stored type and `response-content-disposition=inline`. The signature binds the key, and the key names the document: the link cannot be used for another object, nor after its time, which the storage enforces and the test against MinIO shows with a link made for 1 second.

The browser asks when a block enters the viewport (one link for each image, so a document of many images does not burst the 120 requests a minute of the API row), shows the image from the URL, asks again when four minutes of the five have passed and when the `img` reports an error. A link that was loaded stays shown. A 404 or a missing object shows the statement "no longer available" of Q14.

The page's policy must name the storage's origin in `img-src` and nowhere else (`IMAGE_STORAGE_ORIGIN`, derived from the endpoint and the bucket: `https://<bucket>.fra1.digitaloceanspaces.com`; `http://localhost:9000/<bucket>` for MinIO). That changes the owner's decision of 9 October 2026 ("no remote origins") by one origin, which is row S19-4. The four places that hold the policy as text (`csp.ts`, `csp.test.ts`, `headers.spec.ts`, `fault-page.spec.ts`) change together.

Settings, each with its initial value and a variable (`.env.example`): `IMAGE_STORAGE_ENDPOINT`, `IMAGE_STORAGE_BUCKET`, `IMAGE_STORAGE_REGION` (`fra1`), `IMAGE_STORAGE_ACCESS_KEY_ID`, `IMAGE_STORAGE_SECRET_ACCESS_KEY` (read in `settings.ts` and nowhere else; NFR-SE-19, and not equal to any other secret), `IMAGE_LINK_SECONDS` 300, `IMAGE_DOCUMENT_MEGABYTES` 100, `IMAGE_UNREFERENCED_DAYS` 30. The two processes both load them (the collaboration server writes references, and does not touch the storage).

## 9. Not built, or not testable here, whatever the answer

The Spaces adapter against a real Spaces bucket: `response-content-disposition` and `response-content-type` on a signed link, an `X-Content-Type-Options: nosniff` on the storage's response (an object's headers are the storage's, and nothing on this side can add one), and "no public read, no listing" are properties of the bucket and of DigitalOcean's service that MinIO resembles and does not prove; they are for the owner to check once, when the bucket exists.
