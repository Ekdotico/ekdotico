## 2. The shared channel: Valkey, as built (D165), and why

FR-ED-40 asks Ekdotico to "publish the change to every Hocuspocus instance", and NFR-SE-03 (d) says "over the shared Valkey adapter (NFR-SC-04)". D174 says the ten connections are counted **in the one instance**; D168 and D189 put NFR-SC-04 and the adapter between instances after α. None of them removes the need for a path **from the web application to the collaboration server**: they are two processes (`next start` and `node src/collab/server.ts`), so an in-process call cannot reach the connections even with one instance of each. That path exists since slice 12: the channel `ekdotico:collab-events` (D165), published by the web application after a commit, subscribed by the collaboration server, which does not listen until it is subscribed (`src/lib/collab/events.ts`; the health check says so). This slice **adds two events to it** and builds nothing new: no adapter, no second channel, no dependency.

## 3. Design

**Events** (`src/lib/collab/events.ts`; a member of `CollabEvent`, a case of `readEvent`, a publish after the commit, and a case where the server acts, as the head of the file says). A message holds the kind and identifiers and nothing else (NFR-SE-19):

- `collaborator-changed { documentId, userId }`: (a) a removal or a leave, (b) a change of role. One kind, since the reading is the same.
- `session-ended { userId }`: (d). Published after the commit of a sign-out, the revocation of one session or of the others, a reset or a change of the password, and the confirmation of a change of address. The account's own deletion (slice 22) publishes the same event; the tombstone has no address, so `sessionStands` refuses its sessions.

A publish that fails prints one line (kind, identifiers, class of fault) and never fails the request; the re-check closes what the lost notice left open within 60 seconds (FR-ED-41).

**The collaboration server does not obey an event.** Anything that reaches Valkey can publish one, and a genuine one can arrive after what it tells of was undone. As for the deletion of a document (`endDocument`), the notice makes the server look, by the **rows**. `recheckOnce` takes a scope: with none it is the 60-second run; with the keys of an event it reads, for the open connections that match, the sessions' rows once and `authorise` once for each user and document, and decides with `decide`, the one function of the re-check. So a forged event does nothing but cost a reading, and only where it names an open connection; a flood of them is coalesced (one run at a time and one waiting; past 1,000 keys waiting, the next run is the whole re-check).

- **5 seconds.** The event run bounds each read at 2 seconds (the deletion's, `NOTICE_READ_MS`) and reads the sessions once; where a read fails the connections of the run are closed `unavailable` (S14-3), and the client's handshake reads the row.
- **A stale reading never undoes a fresh one.** A run of the timer and a run of an event can overlap. Each reading of access takes a number from a counter before it starts, and a connection keeps the number of the last decision applied to it; a decision made on an earlier reading than that is dropped. Without it a re-check that read "Editor" a moment before a downgrade could make the connection editable again after the event had made it read-only, for up to 60 seconds.
- **The notice of a switch is sent once** whichever run applies it (it is decided from the connection's state when it is applied).

**The web side** (`src/lib/documents/collaborators.ts`, pure rules in `collaborator-rules.ts`, which the sharing page reads too). Each action is one transaction that **holds the document's row `FOR UPDATE`** (`lockDocument`, as an invitation and its acceptance do), then **reads again** the document's permission set and the actor's own role under the lock: a request that was authorised before an Owner removed the actor, or took the permission away, is refused by what the rows say now, and nothing is changed on what the request was authorised for. The order inside: the document and the actor's role (404 where gone), the permission (403, logged), the collaborator named **of this document** (404; a row of another document is no row), not oneself (403), and, where the actor is not the Owner, not an Editor (403). Then the change, the entry of `collaborators_changed`, the commit, and the publish. A role change to the role held answers 200 and writes, logs and publishes nothing.

**The screens** (the sharing settings, `/documents/[id]/sharing`): in the list of people each collaborator the viewer may act on gets a role control ("Role of [name]", Editor or Viewer) with "Change role", and "Remove"; "Remove" opens a confirmation under rule 13 of the system feedback register, focus on Cancel. A collaborator who is not the Owner sees "Leave document" with the statement before it and the same confirmation, **also where the role's permission set hides the people** (the page said only that it hides them). Controls are withdrawn where the server would refuse; the refusal does not rest on the page.

## 4. Routes, each with its authorisation

Each is made by `documentRoute`, which checks the origin first (D164), then the session's **row** (a state-changing request never uses the cookie cache), then the document and the permission (404 or 403, logged), then the handler reads the body (415 where not JSON, D149). `tests/unit/routes.test.ts` holds each to its permission.

| Route                                                       | Permission                      | Answer                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PATCH /api/documents/[id]/collaborators/[collaboratorId]`  | `document.collaborators.roles`  | Body `{ "role": "editor" \| "viewer" }`, nothing else. 200 with the statement; 404 for a collaborator not of this document; 403 (logged) for oneself, for an Editor where the actor is not the Owner; 422 for any other body and for `reviewer` (FR-ED-44, as invitations) |
| `DELETE /api/documents/[id]/collaborators/[collaboratorId]` | `document.collaborators.remove` | No body. 200 with the statement; 404 and 403 as above                                                                                                                                                                                                                      |
| `POST /api/documents/[id]/leave`                            | `document.leave`                | No body. 204. The Owner holds no `document.leave` (the table: "—"), so 403 (logged), and has no row to remove                                                                                                                                                              |

`GET /api/documents/[id]/collaborators` adds `self: true` to the caller's own entry, so that a page withdraws the controls on it and shows "Leave document"; it carries no account identifier (slice 13).

**Departures from API design, S15-1:** the page names a collaborator by `[userId]` and has one DELETE for removing and leaving. The people list carries no account identifier (the review of PR 43), so the segment is the collaborator's row identifier, and leaving is its own route under its own permission, so that no handler decides between two permissions by whom the path names. FR-ED-38 says further API requests of a removed user "receive a 403 response"; they are answered 404, as for a document that does not exist, by the owner's answer to Q8 of the plan (S15-6).

## 5. The cases

| Case                                                                                                              | What happens                                                                                                                                                           |
| ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The Owner removes an Editor with the document open in two tabs                                                    | Both connections closed `access-ended` within 5 seconds; their places are free; the document leaves the person's list; the next handshake is refused; their edits stay |
| An Editor leaves                                                                                                  | The same, for the leaver's connections; the Owner and others are untouched                                                                                             |
| The Owner changes an Editor to Viewer, and back                                                                   | The connection stays open, read-only in place within 5 seconds and told (`role` notice, slice 14), and editable in place again; what a Viewer sends is discarded       |
| A session is ended by sign-out, by revocation, by a reset of the password, a change of it, or a change of address | Every connection opened under that session closed `session-ended` within 5 seconds; a connection of a session that stands stays                                        |
| The Owner removes someone, and the document is at ten people                                                      | An invitation passes at once                                                                                                                                           |
| An Editor who holds `roles` and `remove` acts on a Viewer / on an Editor / on the Owner (no row) / on oneself     | Done / 403 logged / never a row / 403 logged                                                                                                                           |
| A Viewer, or an Editor without the permission, tries                                                              | 403, logged; nothing changed                                                                                                                                           |
| An account with no role                                                                                           | 404, as for a document that does not exist                                                                                                                             |
| A collaborator's identifier from another document                                                                 | 404; nothing changed in either document                                                                                                                                |
| The actor is removed, or loses the permission, between the authorisation and the transaction                      | 404 or 403 from the rows read under the lock; nothing changed                                                                                                          |
| A role change and a removal of the same person at once                                                            | One after the other: both succeed in that order, or the second finds no collaborator (404); never a fault, never a role on a removed row                               |
| A role change and an acceptance at once                                                                           | Serialised by the row; both stand                                                                                                                                      |
| The publish fails (Valkey does not answer)                                                                        | The change stands, one line says so, the request answers; the re-check acts within 60 seconds                                                                          |
| A forged event for a live connection, a user, or a document that does not exist                                   | Nothing is done to any connection that the rows do not support                                                                                                         |
| A change of role while a full re-check is mid-reading                                                             | The stale reading is dropped; the connection ends as the event left it                                                                                                 |
| The log cannot be written                                                                                         | The transaction fails: no change stands without its entry                                                                                                              |
