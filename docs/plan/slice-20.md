## 2. What stops the slice

**S20-1. A domico gap: the marker and the list of entries have no class.** `@ekdotico/domico` 0.32.0 draws the editor's surface by element and by the classes of its contract ("The document surface": `ekd-editor`, `ekd-code`, `ekd-toc`, `ekd-page-break`, `ekd-image`, the table's). It has nothing for a footnote: a search of the package, its stylesheets, its README and its catalogue for "footnote" finds none. The Docs' own site styles footnotes in `app/globals.css` (`sup[data-footnote-ref]`, `[data-footnotes]`), which is not the package.

The rule of the package is to stop and recommend. What is built does not need a new value: the marker is `sup` holding `a`, which `.ekd-editor` draws as a superscript and a link (the accent, underlined); the entries are an `ol` of `li` with `value` set to the derived number, which the same stylesheet draws as a numbered list. No rule of this repository's own is added for them. What is missing is their own look: a rule above the list that sets it apart from the text, the size and ink of an entry (the caption's: the sans, `--fs-sm`, `--fg-2`), the ring of the marker's focus, and a way to show which entry a marker has just led to.

Recommended (the package's own first choice, extending an existing pattern): `ekd-footnote-ref` for the marker (a `sup` holding an `a`), `ekd-footnotes` for the section that holds the list, `ekd-footnote` for an entry, and `[data-footnote-target]` for the one just reached, in "The document surface", in the next release. When it is released this slice changes the attributes that `MARKER_MARKUP`, `markerView`, `LIST_MARKUP`, `ENTRY_MARKUP` and `numbersOf` of `src/app/(app)/documents/[id]/footnotes.ts` make, and nothing else: the markup is made in those five places for that reason.

## 3. Design

**The schema.** Three nodes, and `doc` takes the list after the blocks: `doc: block+ footnotes?`.

- `footnoteReference`, the marker: an inline atom with one attribute, `id`, which is 24 characters of `0-9a-f` made in the browser from 12 random bytes. It carries no mark. It is a leaf, so the server's rule for blocks that hold nothing (`leaf`) covers it. It stands wherever a paragraph's content can: a paragraph, a heading, a cell, a quote, a callout, a list item; not in a code block, a table caption, or an entry (S20-6).
- `footnotes`, the list: `content: footnote+`, isolating, outside the group `block` so that no block can be put in it and it can be put in no other place. Rendered as `section` (role `doc-endnotes`, named "Footnotes") around an `ol`. It is never parsed from HTML: a pasted list is an ordinary one.
- `footnote`, the entry: a text block of `(text | hardBreak)*` with the nine marks, and the same `id`; isolating, so that Backspace at its start joins nothing. Rendered as `li` with role `doc-endnote`.

**The number is derived and stored nowhere.** The number of a marker is its place among the markers in the order of the document, counting from 1; the number of an entry is the number of its marker. Both are drawn from the text of the editor by a decoration (the marker's view is handed the number; the entry's `li` gets `value`), so two clients that hold the same document draw the same numbers, whatever order they received its changes in and whatever place an entry stands in. A marker whose identifier an earlier marker holds is counted with that one.

**One function says what the list must hold, and what it does is made of changes that touch nothing that stays** (`applyNotes`): one entry for each marker, and none else.

- After a change **this writer** made, in the same transaction, so in the same step of undo: what is not wanted is taken out (an entry of no marker, one without a valid identifier, a second of one identifier; and a marker without a valid identifier, and a second of one identifier), and the entry of each marker that has none is made, empty, at its place in the order of the markers.
- After a change that **arrives from the binding**, another client's or an undo: what is not wanted is taken out, and **nothing is put in**. A deletion that every client makes is the same deletion, so any number of clients doing it converge (an entry twice: each deletes the later and keeps the same first). An entry that every client made would be one for each, so a marker that arrives without its entry waits for the next change of this writer, which makes it.
- Entries are never the writer's to delete or to make: removing the text of an entry empties it; selecting across the list and deleting puts the entries back, empty; to remove a footnote, remove its marker (S20-3).
- **An entry is never written again to put it in the order of the markers.** The binding writes a reorder of same-named elements by writing each in the place of the other, its identifier and its words, so what another writer typed in one in that moment would stand in the other: it was built that way first and a test of two writers showed words typed in one entry appearing in the other. Entries stand in the order their markers had when they were made, which is the order of the markers unless text that holds a marker is moved or two writers put theirs in at one place; each entry is drawn with the number of its own marker whatever its place, so the number is right and the order of the list can lag (S20-11).

**Pasting and dropping.** A copied marker pastes as a new footnote: `transformPasted` gives every pasted marker a new identifier, and its entry is made with the words of the entry it was copied from, from the document where that entry still stands (a copy, a drag), or from what the tab kept when the text was cut (`transformCopied`, in memory, the last 50, one tab). Across tabs and documents the entry is empty (S20-4).

**The palette.** `/footnote` and `/fn`. A row is listed where a marker can stand and the change, with the entry it makes, keeps the limits of the document. A choice puts the marker where the command stood, makes the entry, puts the cursor at the end of the entry, and scrolls it into view; it is one change, and so one step of undo.

**Following a marker.** The marker is a link and a stop of Tab, in the text as well as in a document that cannot be edited. Tab from the text reaches the next marker, Enter on it follows it; a click does the same. Where the document can be edited the cursor goes to the end of the entry and the entry is scrolled to; where it cannot, the entry is scrolled to and takes the focus. An arrow key does not select an inline node in ProseMirror (it moves the cursor over it), so the arrow keys are not the way. The keys pressed on the link are the link's (`stopEvent`): the editor would answer Enter by splitting the paragraph at the cursor. There is no control for going back: no requirement asks for one (S20-8).

**Enter in an entry** makes a line break (the library's own command refuses an isolating block, so the entry has one of its own, for Enter and Shift+Enter) and never a second entry, which would carry the same identifier. A paste into an entry is flattened to inline content by the parser's context.

**The trailing paragraph.** The starter kit adds an empty paragraph at the end of a document that does not end in one, so that the cursor has a place after a table. With the list at the end, that paragraph goes before the list. The kit's own is turned off and one of the same behaviour, placing the paragraph before the list, replaces it, in `footnotes.ts`; `deletesOnly` of `block-limits.ts` knows where it goes.

## 4. The server

`src/lib/collab/shape.ts` keeps `NODES` equal to the editor's schema (the existing test fails where they differ): `footnoteReference`, `footnotes`, `footnote`, and `doc: block+ footnotes?`. The new rules, as the image's are, answered with the copy of the document and without it, which agree:

- The attributes of a marker and of an entry are `id` and nothing else, and its value is a string of the form above or null. Refused, whatever the Yjs content that carries the value: a plain value, JSON, an embed, binary data, a subdocument, a shared type, or a format; and an item that replaces an earlier value, which has no name of its own. The refusal is `footnote-attributes`.
- A marker holds nothing (`leaf`).
- `footnote` is one of `ONE_BLOCK`; `footnotes` is counted by what it holds, as a list is.

The reason is `REFUSAL.FOOTNOTE_ATTRIBUTES`, mapped in `src/collab/server.ts` and held by the client like `image-attributes`. An empty `footnotes` is refused as `incomplete`, as any element without its required content.

## 6. Accessibility (WCAG 2.2 AA, NFR-IC-19)

The marker is a link (`a` with `href="#footnote-…"`, role `doc-noteref`) named "Footnote 3", whose visible text, "3", is in its name (2.5.3). The entry is a list item (`doc-endnote`) in a list in a region named "Footnotes", read with its number (`value`). The way from the text to an entry is by keyboard alone (2.1.1): Tab reaches the next marker and Enter follows it, in a document that can be edited and in one that cannot; the keys pressed on the link do not reach the editor. The way back is not built (S20-8). Nothing depends on colour. No movement or drag is asked for (2.5.7). The size of the marker's target is the package's rule for a link in the editor (2.5.8) and is not measured here: it is part of S20-1. No automated accessibility checker is a dependency of the repository yet (plan row C5, "recorded with their versions when first used"), so the roles, the names, the focus and the keys are asked of the browser by the test, which is what the checker would read. No screen reader was run.

## 10. What building it found

- The page hands a node view its decorations when it makes the view and calls `update` only when they change: a marker that drew itself from `update` alone was empty.
- The library's `setHardBreak` refuses an isolating block, so Enter and Shift+Enter in an entry have a command of their own; without it Enter split the entry, and the second of one identifier was taken out at once, so the cursor stayed where it was.
- ProseMirror does not select an inline node with an arrow key, and the first design of the keyboard way (arrow, then Enter) did not work; the marker is now a stop of Tab, which a test of a browser asks for.
- The binding writes a reorder of entries in place, so a rule that put the list in order lost, or misplaced, words typed meanwhile (a test of two writers showed `Bb!` in the wrong entry). The rule now never writes an entry again; section 3, S20-11.
- The end-to-end tests first moved the cursor with the keys for the start of a document, which differ by platform and moved nothing on this machine; and a change the editor applies between the press of the pointer and its reading of it (the drawing of another client's cursor) writes the old selection over the new, as ProseMirror does everywhere. The helper looks in the editor's state and presses again.
