## 2. What stops the slice

**S20-1. A domico gap: the marker and the list of entries have no class.** `@ekdotico/domico` 0.32.0 draws the editor's surface by element and by the classes of its contract ("The document surface": `ekd-editor`, `ekd-code`, `ekd-toc`, `ekd-page-break`, `ekd-image`, the table's). It has nothing for a footnote: a search of the package, its stylesheets, its README and its catalogue for "footnote" finds none. The Docs' own site styles footnotes in `app/globals.css` (`sup[data-footnote-ref]`, `[data-footnotes]`), which is not the package.

The rule of the package is to stop and recommend. What is built does not need a new value: the marker is `sup` holding `a`, which `.ekd-editor` draws as a superscript and a link (the accent, underlined); the entries are an `ol` of `li` with `value` set to the derived number, which the same stylesheet draws as a numbered list. No rule of this repository's own is added for them. What is missing is their own look: a rule above the list that sets it apart from the text, the size and ink of an entry (the caption's: the sans, `--fs-sm`, `--fg-2`), the ring of the marker's focus, and a way to show which entry a marker has just led to.

Recommended (the package's own first choice, extending an existing pattern): `ekd-footnote-ref` for the marker (a `sup` holding an `a`), `ekd-footnotes` for the section that holds the list, `ekd-footnote` for an entry, and `[data-footnote-target]` for the one just reached, in "The document surface", in the next release. When it is released this slice changes four attribute values in `src/app/(app)/documents/[id]/footnotes.tsx` and nothing else: the markup is made in one place for that reason.

## 3. Design

**The schema.** Three nodes, and `doc` takes the list after the blocks: `doc: block+ footnotes?`.

- `footnoteReference`, the marker: an inline atom with one attribute, `id`, which is 24 characters of `0-9a-f` made in the browser from 12 random bytes. It is a leaf, so the server's rule for blocks that hold nothing (`leaf`) covers it. It stands wherever a paragraph's content can: a paragraph, a heading, a cell, a quote, a callout, a list item; not in a code block, a table caption, or an entry.
- `footnotes`, the list: `content: footnote+`, isolating, outside the group `block` so that no block can be put in it and it can be put in no other place. Rendered as `section` (role `doc-endnotes`, named "Footnotes") around an `ol`.
- `footnote`, the entry: a text block of `(text | hardBreak)*` with the nine marks, and the same `id`. Rendered as `li` with role `doc-endnote`.

**The numbering is derived and stored nowhere.** The number of a marker is its place among the markers in the order of the document, counting from 1; the number of an entry is the number of its marker. Both are drawn from the text of the editor by a decoration, so two clients that hold the same document draw the same numbers, whatever order they received its changes in. A document with a marker whose id is held by an earlier marker counts that marker once.

**One function says what the list must be, and one rule applies it.** `notesOf(doc)` reads the markers (the first of each identifier; a marker without a valid identifier is no marker) and the entries, and returns the list that the document must hold: one entry for each marker, in the order of the markers, each the entry the document already has for that identifier, or a new empty one. The list is the same function of the markers for every client. A plugin, after each transaction that **this writer** made (never one that arrives from the binding or from an undo), asks for it and, where the list differs, replaces the differing middle of the list with it, in the same transaction and so in the same step of undo. That is the whole of the behaviour of the list:

- A marker put in (the palette, a paste, a drop) has its entry made. A marker taken out (deleted, cut, text deleted round it) has its entry taken out with it. Undo brings both back.
- Entries are never the writer's to delete or to make: removing the text of an entry empties it; selecting across the list and deleting puts the entries back, empty; to remove a footnote, remove its marker. (S20-3.)
- Text carrying a marker, moved, puts the entries in the new order, so the list is in the order of the numbers (FR-ED-05, "reordered").
- Two writers who add footnotes at once each put in a marker and an entry; Yjs keeps both, and the list is already what the function says, so nothing more is written. Where a list is wrong because of what two writers did (an entry twice, an entry of a marker that another writer deleted, a marker whose entry was taken out), the next change by anyone puts it right by deletions and by one insertion of an empty entry of a known identifier, so any number of writers doing it at once converge (a second entry of one identifier is deleted by each of them, and the first is the same entry for each). The one case that loses text is two writers each putting in the first footnote of a document at the same moment: the second list is taken out by the schema's repair, with its entry, and the marker's entry is made again empty. Tested; stated (S20-9).

**Pasting and dropping.** A copied marker pastes as a new footnote: `transformPasted` gives every pasted marker a new identifier, and makes its entry with the words of the entry it was copied from, from the document where that entry still stands (a copy, a drag), or from what the tab kept when the text was cut (`transformCopied`, in memory, the last 50, one tab). Across tabs and documents the entry is empty. (S20-4.)

**The palette.** `/footnote` and `/fn`. A row is listed where a marker can stand and the change keeps the limits of the document (the entry is a block of the 5,000). A choice puts the marker where the command stood, makes the entry, puts the cursor at the end of the entry, and scrolls it into view; it is one step of undo. Where a document is at its limit the row is not listed, as for every block.

**Following a marker.** A click on the marker, and Enter on a marker that the arrow keys have selected, put the cursor at the end of its entry and scroll the entry into view; in a document that cannot be edited the entry is scrolled to and takes the focus. There is no control for going back: no requirement asks for one (S20-8).

**Enter and paste in an entry.** Enter makes a line break and never a second entry, which would carry the same identifier. A paste into an entry is flattened to inline content by the parser's context.

**The trailing paragraph.** The starter kit adds an empty paragraph at the end of a document that does not end in one, so that the cursor has a place after a table. With the list at the end, that paragraph goes before the list. The kit's own is turned off and one of the same behaviour, placing the paragraph before the list, replaces it, in `footnotes.tsx`.

## 4. The server

`src/lib/collab/shape.ts` keeps `NODES` equal to the editor's schema (the existing test fails where they differ): `footnoteReference`, `footnotes`, `footnote`, and `doc: block+ footnotes?`. The new rules, as the image's are, in the copy of the document and without it:

- The attributes of a marker and of an entry are `id` and nothing else, and its value is a string of the form above or null. Refused, whatever the Yjs content that carries the value: a plain value, JSON, an embed, binary data, a subdocument, a shared type, or a format; and an item that replaces an earlier value, which has no name of its own. The refusal is `footnote-attributes`.
- A marker holds nothing (`leaf`).
- `footnote` is one of `ONE_BLOCK`; `footnotes` is counted by what it holds, as a list is.

The reason is `REFUSAL.FOOTNOTE_ATTRIBUTES`, mapped in `src/collab/server.ts` and held by the client like `image-attributes`. An empty `footnotes` is refused as `incomplete`, as any element without its required content.

## 6. Accessibility (WCAG 2.2 AA, NFR-IC-19)

The marker is a link (`a` with `href="#footnote-…"`, role `doc-noteref`) named "Footnote 3", whose visible text, "3", is in its name (2.5.3); the entry is a list item (`doc-endnote`) in a list in a region named "Footnotes", read with its number. The marker is reached from the text by the arrow keys, which select it, and Enter follows it; it is a link in a document that cannot be edited and is reached by Tab. Nothing depends on colour. The target of a click is the whole of the marker's number, at least 24 CSS pixels square for the reader of a document that cannot be edited (2.5.8), by the package's rule for a link in the editor, not by a rule here. No movement or drag is asked for (2.5.7). Reflow and zoom are the surface's.
