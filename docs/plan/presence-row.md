## 2. Design

### 2.1 Who is present

The server already pins the name and the slot of each connection into its awareness state (slice 14). The role is **not** put there. Awareness is one state for every peer, sent by a client under its own clock: a role that changes on the server cannot be written into it again without racing the client's next update (the server's clock would be ahead, and the client's next state is ignored until its own catches up), and a state cannot be withheld from the one recipient whose permission set hides the roles.

So the server sends a **stateless message** `{"kind":"people","people":[{"slot","name","role"?,"you"?}]}`, to each open connection of the document, personally:

- One entry for each connection **whose place is held** (the `connected` hook has run; one still being made is not listed, so no list holds an eleventh and none holds a connection that is about to be closed), in the order of the slots. A second tab of the same account is a second entry, as it holds a second place (PR-3).
- `name` and `slot` are the place's (read from the account by the server, never from the client). `role` is the connection's role as the server holds it, **only for a recipient whose role holds `document.collaborators.view`** (FR-ED-44: adjustable; the Owner can turn it off) (PR-2). `you` is true on the recipient's own entry.
- Sent when a connection is made, when one closes, and when one is switched (a role or a permission set that changed), to every connection of the document. At most ten recipients; a flood of reconnections is bounded by the limit of handshakes.
- The client reads it strictly, field by field (`readPeopleNotice`), as it reads the role notice, keeps the last list (`ConnectionState.people`), and takes it away when the connection is lost for good (the phase `lost`): a list that the server can no longer keep true is not shown. A peer cannot send one: the server relays no stateless message a client sends.

**The row** (`src/app/(app)/documents/[id]/people-row.tsx`) is `AvatarStack` of `@ekdotico/domico` 0.31.0: the initials on the colour of each person's slot, which is the colour of their cursor; `avatarInitials` of the package writes the letters, by whole grapheme and with `toUpperCase`, so a Greek name is not cut and the letters are the same on every machine (a function of ours that skipped brackets and emoji was dropped for it). To a screen reader it is a list named "People in this document" whose items read "[Name] (you), [Role]"; it is not a tab stop, since nothing in it acts. The role is read only where the server sent it (PR-2).

**Where.** In the header of the document, in the one cluster with the title and "Sharing". The two answer one question, who is on this document, and the header is the part of the page that stays above the text and is reached before it, by a reader and by a screen reader alike; the row is a place a person looks at a glance and does not scroll to. The page, which is a server component and holds no connection, renders an empty place and the editor, which holds the connection, fills it by a portal; the place takes no room until it is filled, and the cluster wraps at 320 pixels.

### 2.2 The limit on presence messages (S14-5)

`AWARENESS_PER_SECOND = 60` in `src/lib/collab/presence.ts`, kept for each connection in a sliding window of one second (the times of its last 60 messages): a message is let through where fewer than 60 were let through in the second before it. Counted in `beforeHandleMessage`, which sees every message before it is decoded. A message of the awareness type past the limit is **dropped, not closed**: it is made to speak for no one, so `beforeHandleAwareness` removes every state in it and the update that goes on is empty; a peer receives nothing for it and the connection is kept.

A **request for everyone's awareness** (message type 3) is counted in the same window. The library builds the awareness of every client for each one and offers no way to refuse a message but by closing the connection, and the provider of this application sends none; so past the limit it **closes** the connection (PR-11). Messages that carry an update are not counted (the 600 messages of NFR-SE-07 count those).

### 2.3 A downgrade handles what was received first (F14-2)

`recheckOnce` switched a connection to read-only at once, so a message already received and still being handled could find the flag turned and be discarded. Now a switch that changes the flag, in either direction, first waits for `connection.waitForPendingMessages()`: for an upgrade (as slice 14 built) so that no update that was not checked is applied; for a downgrade so that what the server had received while the person was an Editor is kept. The wait is for the connection's queue to empty, so **a message that arrives during it is handled too, as the old role, up to the bound**. After the flag turns nothing is accepted: the library tests the flag at each update.

The wait is **bounded** (`PENDING_WAIT_MS`, 1,000 ms; `CollabOptions.pendingWaitMs` for a test), because a client that never stops sending would otherwise keep a downgrade from ever being applied. At the bound a downgrade **switches anyway** (a message still waiting is discarded, and one line says so, naming no one). An upgrade at the bound is **not made**: the connection stays read-only until the next look, which is the next event that names it or, at the latest, the next re-check (up to 60 seconds, FR-ED-41), and one line says so. **The budget** of FR-ED-40's 5 seconds, for a change that an event announces: the sessions are read for at most 2 seconds, the access for at most 2, and this wait for at most 1; they add to 5, so a slow database and a connection that never stops sending together use all of it (PR-7). The waits for the connections of a run are not one after another: a switch that waits does not hold back a close that another connection of the run needs.

### 2.4 The tab says that its last changes were not saved (F14-2)

The server answers each update and each second step with one status, in order: 1 where it applied the message, 0 where it did not (a read-only connection applies nothing). The tab keeps the messages that wait for their status in the order they left, each with the next clock of its own changes when it left, and **`acknowledged` is the clock of the last one the server applied**. The provider's own count cannot say this: it counts a batch, it is set to 1 at every connection whether or not a change waits, and a status of 0 does not lower it (two reviewers found the false offers that followed). A first step sent on a new socket ends the wait for what was sent before it (it will not be answered on that socket), and what held changes is `carried` until a second step is answered as applied, which carries the whole document. A status of 0 for a message that held changes makes them `carried` too.

`unsentText` (`src/lib/collab/unsent.ts`, no I/O) reads from the document the text that this client wrote since `acknowledged` and that still stands, in the order of the document, one passage for each run of words. The client keeps it in `ConnectionState.unsaved` when it is told (or finds at a new handshake) that its role cannot edit and it holds changes that the server did not apply. **It is worked out again with every status that follows:** an acknowledgement that comes after the notice takes the offer back, and a refusal leaves it; and it is taken away when the connection may edit again (the client then sends what it holds, slice 14) and with the connection. A notice can therefore be made and withdrawn within a moment, where a status was still on its way (PR-12).

### 2.5 The notifications (S15-2)

Two kinds, `role_changed` and `removed`, in the table `Notification` that slice 13 wrote (no migration: `kind` is text and `payload` is JSON), written by the same transaction as the change (`changeRole`, `removeCollaborator` of `src/lib/documents/collaborators.ts`), so a change never stands without its notification and the reverse. The module that writes and lists them is its own (`src/lib/documents/access-notifications.ts`), so that the parallel work on ownership offers touches `listNotifications` in one place only.

- The recipient is the person affected, never the person who acted: the writers refuse an actor as recipient, and a leave writes none.
- The payload holds identifiers and the role and nothing else (never a title): `{ documentId, role }` and `{ documentId }`.
- **What ends a `role_changed` notification (PR-10), as FR-ED-42 says, "until its subject no longer exists".** Its subject is the person's role, which ends when the role is changed again, when the person is removed, and when the person leaves, and a person who is invited again holds a new role and not the one an old notification names. So each of those transactions **deletes** the person's earlier `role_changed` rows for that document, and the list shows one only while the person holds a role on a document that is not deleted. The permanent deletion of a document takes its notifications with it.
- `role_changed` shows the title of the document read when the list is read, and links to the document. The recipient holds a role, so this is no secret, and D202's rule (a title shown to an invitee, who holds none) is not what is followed or broken here.
- `removed` names no title and links to nothing (PR-5). It stays 30 days (PR-8): the list shows it for that long, and **the timer of the application deletes it after** (`removed-notification-removal` among the timers of `src/lib/timers.ts`, NFR-RE-15, hourly).
- Read with "Mark as read" as the invitation's. A notification with no link (a removal) takes the focus to its own words when it is marked read (WCAG 2.4.3).

## 7. Not done, and said plainly

- A screen reader is not run on the row (its list is read from the accessibility tree by Playwright's ARIA snapshot); a browser other than Chromium is not run; no phone width but the 320 pixels of the row.
- Nothing runs with two instances (D168, D189).
- A display name changed in the account's settings is shown from the next connection (slice 14); the row says the same.
- A change in the people present is sent to every connection of the document; no further limit is put on how often it is sent.
- The row has no name on hover or press: the pictures are initials and a count, and domico builds no more (a name on a control is for when a person has an action).
- A change that only deleted text is stated as unsaved with nothing to copy (PR-6).
