## 2. Design

### 2.1 Who is present (data only)

The server already pins the name and the slot of each connection into its awareness state (slice 14). The role is **not** put there. Awareness is one state for every peer, sent by a client under its own clock: a role that changes on the server cannot be written into it again without racing the client's next update (the server's clock would be ahead, and the client's next state is ignored until its own catches up), and a state cannot be withheld from the one recipient whose permission set hides the people.

So the server sends a **stateless message** `{"kind":"people","people":[{"slot","name","role"?,"you"?}]}`, to each open connection of the document, personally:

- One entry for each connection (a second tab of the same account is a second entry, as it holds a second place; row PR-3), in the order of the slots.
- `name` and `slot` are the place's (`Places`, read from the account by the server; never from the client). `role` is the connection's role as the server holds it, **only for a connection whose role holds `document.collaborators.view`** (FR-ED-44: adjustable; the Owner can turn it off), so that the list does not show to a role the roles of the others that the people list on the sharing page hides from it (row PR-2). `you` is true on the recipient's own entry.
- Sent when a connection is made (`connected`), when one closes, and when a connection is switched (a role or a permission set that changed), to every connection of the document. At most ten recipients; a flood of reconnections is bounded by the limit of handshakes.
- The client reads it strictly, field by field (`readPeopleNotice`), as it reads the role notice. A peer cannot send one: the server relays no stateless message a client sends.

The client keeps the last list in its state (`ConnectionState.people`), and `initialsOf(name)` writes the two letters of a picture: the first letter of the first and of the last word of the name, in capitals, by code point and not by byte (the names are often Greek), or the first letter alone for one word. The colour of a picture is the slot's, as the cursor's is.

**What waits for domico.** A stack of pictures, its overflow count, the list a screen reader reads, and their place in the header near Sharing. The component should come from `@ekdotico/domico` (AGENTS.md, rule 4, and "A component used twice comes from the package"). A list with a swatch and a name beside it is a pattern the design package already allows (`docs/design-tokens.md`, "Collaborator": "a list of who is present carries the name beside the swatch"); it is not a stack of pictures, which is what the owner chose, and a stand-in list would be written twice. Row PR-1 says what to add.

### 2.2 The limit on presence messages (S14-5)

`AWARENESS_PER_SECOND = 60` in `src/lib/collab/presence.ts`, kept for each connection in a sliding window of one second (the times of its last 60 messages): a message is let through where fewer than 60 were let through in the second before it. Counted in `beforeHandleMessage`, which sees every message before it is decoded. A message past the limit is **dropped, not closed**: it is made to speak for no one (`speaking` is empty), so `beforeHandleAwareness` removes every state in it and the update that goes on is empty. A peer receives nothing for it and the connection is kept; the next message after the second is handled as usual. A message that is not awareness is never counted (the 600 messages of NFR-SE-07 count those that carry an update).

### 2.3 A downgrade handles what was received first (F14-2)

`recheckOnce` switched a connection to read-only at once, at the moment the decision was applied, so a message already received and still being handled could find the flag turned and be discarded. Now a switch that changes the flag, in either direction, first waits for `connection.waitForPendingMessages()`: for an upgrade (as slice 14 built) so that no update that was not checked is applied; for a downgrade so that what the server had received while the person was an Editor is kept. After the flag turns nothing is accepted: the library tests the flag at each update (`MessageReceiver`).

The wait is **bounded** (`PENDING_WAIT_MS`, 1,000 ms; `CollabOptions.pendingWaitMs` for a test), because a client that never stops sending would otherwise keep a downgrade from ever being applied, which FR-ED-40 and FR-ED-41 do not allow. At the bound a downgrade **switches anyway** (a message still waiting is discarded: one line says so, naming no one) and an upgrade is **not** made (it stays read-only; the next look makes it). The waits for the connections of a run are not one after another: a switch that waits does not hold back a close that another connection of the run needs inside the 5 seconds.

### 2.4 The tab says that its last changes were not saved (F14-2)

What the tab holds that the server has not received is the changes of its own client identifier from the clock at which every change was last acknowledged (`acknowledged`, noted whenever the provider's count of unacknowledged messages reaches zero). Whether the tab holds any is a flag of its own (`unacknowledged`, set by a change of the tab's own and cleared at that same moment), and not the provider's count: the library sets its count to 1 at every connection, for the answer to its first step, so a tab that reconnects with nothing to send would otherwise be told that its last changes were lost. The server answers each update it handled with an acknowledgement before it tells the new role, so when the notice arrives anything still unacknowledged is what the server did not take: what was typed offline, and what was sent after the switch.

`unsentText` (new, `src/lib/collab/unsent.ts`, no I/O) reads those changes from the document: the text that this client wrote since that clock and that still stands, in the order of the document, one paragraph for each block it is in. The client keeps it in `ConnectionState.unsaved` when it is told (or finds at a new handshake) that its role cannot edit and it holds unacknowledged changes; it is taken away when the connection may edit again (the client then sends what it holds, slice 14) and with the connection.

### 2.5 The notifications (S15-2)

Two kinds, `role_changed` and `removed`, in the table `Notification` that slice 13 wrote (no migration: `kind` is text and `payload` is JSON), written by the same transaction as the change (`changeRole`, `removeCollaborator` of `src/lib/documents/collaborators.ts`), so a change never stands without its notification and the reverse. The module that writes and lists them is its own (`src/lib/documents/access-notifications.ts`), so that the parallel work on ownership offers touches `listNotifications` in one place only: to add the kind to the list it merges.

- The recipient is the person affected, never the person who acted: the writers refuse an actor as recipient, and a leave writes none.
- The payload holds identifiers and the role and nothing else (never a title): `{ documentId, role }` and `{ documentId }`.
- `role_changed` is shown while the recipient still holds a role on a document that is not deleted (the subject: the role), with the title of the document read when the list is read, and links to the document. The recipient holds a role, so this is no secret, and D202's rule (a title shown to an invitee, who holds none) is not what is followed or broken here.
- `removed` names no title and links to nothing: a person who no longer holds a role is shown nothing of the document that D202 does not say may be shown (row PR-5). It stays in the list for 30 days, as the notice of a clearing that deleted a document does (FR-ED-42).
- Read with "Mark as read" as the invitation's. A notification with no link (a removal) takes the focus to its own words when it is marked read (WCAG 2.4.3).
- The permanent deletion of a document, at the end of its retention, takes the notifications that name it with it.
