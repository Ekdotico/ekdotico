## 2. What the specification already settles, and what is built on it

- **The table shows every permission of FR-ED-44 and every role. Decided by the owner on 19 October 2026 (S16-1).** The permissions α has are 12, in the order of the table: view, edit content, see the collaborators, rename, draft export, invite, change a role, remove, leave, change the permission set, transfer ownership, delete (build-phases, "The permission set of a document, and its settings"). The two comment rows, the sealed export row and the Reviewer column (D56) are not offered in this release: as first built they were hidden (FR-ED-44: the comment rows "are not shown until the role is offered"); the owner decided that they are **shown**, the cells that can be changed as disabled checkboxes with an accessible description, and the server still refuses a change to one with a 422 `not_offered`. The columns are Owner, Editor, Reviewer and Viewer.
- **Authorisation before validation, so 403 before 422** (the owner's answer to Q8 of the plan, and slice 15): FR-ED-45 gives both 422 "whoever asks" and 403 for a user who is not the Owner; a non-Owner who asks for a fixed cell is answered 403. The Owner who asks for a fixed cell is answered 422. An account with no role is answered 404.
- **The request to the server needs no screen** (FR-ED-45: "does not rest on what the settings screen offers"). The screen is built from the same function that decides what a cell is (`permission-rules.ts`), and the route asks again.

## 3. Design

**The set.** `Document.permissionSet` (JSON) holds, for every permission of the table and every role, whether the role holds it, **fixed cells included** (FR-ED-45: stored whole; `defaultPermissionSet`). A change is read-modify-write **under the document's row** (`lockDocument`, as an invitation and slice 15 do), and the new set is written whole: each cell the table fixes takes the table's value, each adjustable cell is the stored value where it is exactly `true` or `false` (`holds`) and the change over it. A change cannot write a fixed cell, so the stored set stays what `holds` already ignores for those cells (`holds` answers the table's value for a fixed or "never" cell and never reads the stored one, so an altered stored set cannot give a Viewer the content).

**Cells** (`src/lib/documents/permission-rules.ts`, pure, loads in a browser): for a permission and a role, one of

- `always` / `never`: the table says `yes` (or `no` for the Owner and leaving) or `never`. On the screen the words; a change is refused **422 `cell_fixed`**.
- `adjustable`: `on` or `off` for Editor or Viewer, for a permission of the 12. A checkbox; a change is accepted.
- `not offered`: the Reviewer column, the two comment rows, and the sealed export row. Shown on the screen, the cells that can change as disabled checkboxes (S16-1, decided by the owner on 19 October 2026). A change is refused **422 `not_offered`** (S16-1). The stored cells stay and are written back unchanged, and a reset returns the whole stored set, those cells included, to the defaults.

**Routes** (API design, "Sharing"; each is made by `documentRoute`: the origin first for a PUT (D164), the session's row, the document and the permission, then the body):

| Route                                 | Permission                   | Answer                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/documents/[id]/permissions` | `document.view` (every role) | The Owner: `{ role: "owner", set }`, the whole stored set. Any other role: `{ role, permissions }`, the identifiers of the permissions of the 12 that the role holds, and nothing of the set                                                                                                                                                                                                                                                              |
| `PUT /api/documents/[id]/permissions` | `document.permissions.edit`  | Body exactly `{ "changes": { "<permission>": { "<role>": true \| false } } }` or `{ "defaults": true }`, at most 4 KB. 200 `{ message, set }`; 422 `invalid_request` for any other body (a key more, a value that is not a boolean, an unknown name, an empty `changes`); 422 `cell_fixed`, 422 `not_offered`; 403 (logged) for a role that does not hold it; 404. A request that changes nothing answers 200, writes, logs and publishes nothing (S16-5) |

All cells are checked before any is written: a refused cell refuses the request and nothing changes. Under the lock the caller's role and permission are read again (as slice 15), so a request authorised before a transfer of ownership, or before the caller was removed, is refused by what the rows say now.

**The event** (`src/lib/collab/events.ts`; as its head says: a member of `CollabEvent`, a case of `readEvent`, a publish after the commit, a case where the server acts): `permission-set-changed { documentId }`, published after the commit and only for a change that was made. The collaboration server does not obey it (as for every event): it **looks** at every open connection to that document (`recheckOnce` with the key of the document) and decides by the rows with `decide`, the one function of the re-check. **`decide` reads the permission set and not the role alone**: it builds the new record with `recordConnection(session, document, role)`, which holds each permission that `holds(document.permissionSet, role, permission)` says, and answers `switch` where the role or the list of permissions differs (a test: a set change with the role unchanged is a `switch`; and the mutation that compares the role alone fails it).

What a switch does is slice 14's and 15's: the record is written into the connection, the connection stays open, editable or read-only as `isReadOnly(record)` says. Added: where the **role is unchanged and the permissions differ**, the server sends a second stateless message, `{ "kind": "permissions", "role": … }`, to that connection. A role that changed is told by the role notice as before and gets no second one (the new role's permissions are what the notice speaks of). A connection whose own role's cells did not change (the Owner's never do) is told nothing. The notice is sent once, whichever run applies the switch (the number of the reading, slice 15).

**The client** (`src/lib/collab/client.ts`, `editor.tsx`) reads the new kind with `readPermissionsNotice` (field by field, as the role notice) and keeps it in its state; the editor states it in a polite status, said again for each change (keyed as the role statement is). **No control on the page of a document is governed by an adjustable permission in α 0.1.0**: renaming is on the list of documents, the draft export button arrives with slice 21, and the people and invitations are on the sharing page, which is read from the server on each load. So there is nothing yet to show or to withdraw; slice 21 reads the held permissions where it adds the control (S16-6). What the requirement fixes — that the client is told and states it — is built and tested.

**The sharing page** reads the document with `authorise` on each request, as every page does.

## 5. The screen (the sharing settings, `/documents/[id]/sharing`)

A section "Permissions" before "Leave document", in the page's own column. All controls are the package's (`Table`, `Checkbox`, `Button`, `Dialog`, `FormFault`; `Checkbox` is in 0.29.0, so FR-ED-46's "added there first" is satisfied); every value in a stylesheet is a token.

**To the Owner**: a table named "Permissions of each role", one row for each of the 15 permissions, in the wording of the first column of FR-ED-44 (S16-2), as a row header; the columns Permission, Kind, Owner, Editor, Reviewer (not offered in this release), Viewer (header cells for both axes). **The cells and rows that α does not offer (S16-1)**: the four cells that could be changed (the Editor and Reviewer cells of "Resolve and reopen any comment thread", the Reviewer cells of "See the list of collaborators" and "Draft export") are disabled checkboxes, named like the others and described for a screen reader by "The Reviewer role is not offered in this release." (the Reviewer's) or "This permission is not offered in this release." (the comment row's Editor cell); the other cells of the Reviewer column and of the three rows that are not offered keep their "Always" and "Never"; each of the three rows says "Not offered in this release." under its name, and the Reviewer's header says "Reviewer (not offered in this release)". **The Owner's "Leave" cell (S16-3)** reads "Never", and the sentence "You are the Owner. You must transfer ownership before leaving." is shown under the row's name and is in the cell for a screen reader, hidden there from it once so that it is not read twice: as the cell's text it would make the column wider than the table is usable at 320 px. The kind is in words ("Fixed by role", "Adjustable", "Fixed to the Owner"). A cell the Owner cannot change shows "Always" or "Never": text, not a disabled control. A cell the Owner can change is a checkbox, **named "[Role]: [permission]"** (for example "Editor: Rename the document") by a label that is visually hidden, so that the name is stated by the control (FR-ED-46) while the page shows the box and nothing else in the cell; no state is shown by colour alone (the box shows a mark). The rows for changing a role and for removing a collaborator carry, in words, that an Editor who is given the permission can act on Viewers and never on another Editor (S16-4). A change is **saved when it is made**: the box is not disabled while the request is out, since a control that is disabled loses the focus, and the requests of the table go one after another; the text beside it, in a polite live region (`aria-live`, not `role="status"`, which the page's own statement holds alone), says "Saved." or the refusal, and the checkbox is described by it; on a refusal the box returns to its stored state and the text stays beside it; focus does not move. One control, "Reset to defaults", opens a dialog under rule 13 of the system feedback register (focus on Cancel) and, confirmed, returns the whole set and says so in a status.

**To any other role**: a section "Your role" saying in words the role held and, as a list, what it may do, from the same 12 rows (`holds` on the stored set); no control. It is shown whether or not the role's set shows the people (the page's earlier statement for that case stays).

Since `@ekdotico/domico` 0.30.0 (S16-8, closed) the package draws a header cell in a table body as the header of its row, types `scope`, and keeps the hidden label of a checkbox (`labelHidden`) inside the label, so the screen carries no stylesheet for any of it; `permissions.module.css` holds placement only. Two descriptions have no package component and are attributes: the disabled checkbox's `aria-description`, and the Owner's "Leave" cell, which is described (`aria-describedby`) by the sentence under the row's name. A hidden sentence in a cell widened the page to 398 CSS pixels at a width of 320 (found by the check for sideways scroll), which is why neither is a hidden element.

A change made by the Owner in one tab is not shown in another tab until it is loaded again; the server decides on every request.

## 6. Tests (each fails when its rule is broken)

Unit: `permission-rules` (every permission and every role: which kind of cell it is; the body reader: every refusal; the list of the 12 offered and of the three offered columns; the table's 15 rows and four columns, and which cells are shown disabled, each refused by the reader of a body); `readEvent` for the new kind; `readPermissionsNotice`; `decide` for a set-only change (a `switch` with the role unchanged, nothing when the same set is read, and the role-or-set change that closes); the client reading the notice; routes and origin tests pick up the two handlers.

Integration (one file at a time):

- `tests/integration/permissions-matrix.test.ts`, the NFR-SE-04 test. **For every one of the 15 permissions and each of the four roles**, through `authorise`, against the printed table: the default answer; for each adjustable cell the answer after the Owner gives it and after the Owner takes it back; the fixed and "never" cells **after the Owner has asked the route** (refused) and after a stored set altered by hand (still the table's). Then **through a real route**, for each permission that has one, for each role, a fresh document each time: the status under the default (403 or success), then, for an adjustable cell, the Owner grants it by the route and **the same session** now succeeds. Permissions with no route yet are said so in the test and are tested through `authorise` alone: edit content (the collaboration server decides it: tested in `collab-permissions.test.ts`), the two comment permissions, the draft export (slice 21), the transfer (17), the sealed export.
- `tests/integration/permission-settings.test.ts`, the PUT and GET routes as Next.js calls them: every cell of the table asked by the Owner with both values (200 for exactly the adjustable cells of Editor and Viewer, 422 for the rest, the stored set unchanged for each refusal); a non-Owner asking each cell (403 for all, logged); IDOR across documents; no role is 404; the session's row and never the cookie cache; the origin first (`route-origin`); a body that is not JSON, too long, with a key more, a non-boolean, a prototype key, an array; two cells with one fixed; the entries of the log (one for each request that changed, with the user and the document and nothing else; none for a refusal but a `forbidden` for a 403; none for no change), written in the transaction (no entry and no change where the log cannot be written; no change where the entry cannot be); the row lock (a transaction of the test holds the row; the request waits; two requests at once both stand; an actor who lost authority while waiting); what was published, byte for byte, after the commit and only for a change, and a failed publish; the reset (whole set, the Reviewer and comment cells included); GET gives the Owner the set and another role the list of its permissions and nothing else; a deleted and restored document keeps the set; a set written by hand with a cell that is not a boolean is read as refusing and a change writes it whole again.
- `tests/integration/collab-permissions.test.ts`, the **real collaboration server and Valkey**, its re-check an hour so that only the event acts: the Owner's change by the route, and the effect on each open connection **within 5 seconds, measured**: an Editor's connection stays open and editable and is told; a Viewer's stays read-only and open; the Owner's is told nothing; a change of a cell of another role tells no one of the first; another document untouched; a forged event harmless; the notice sent once; a change of role and of the set together tells the role only; sign-in-free (the cookie of the session is not renewed); a Viewer given every cell it can hold never becomes editable (what a Viewer sends is discarded); the handshake after the change reads the new set.
- `route-origin.test.ts` gains the PUT: another origin is refused before any session is read.

End to end (Chromium), `tests/e2e/permissions.spec.ts` (the file that runs the collaboration server is `editor.spec.ts`, which gains one case for the statement on an open page): the screen for the Owner (the table of 15 rows and four columns, its headers with `scope`, the four disabled checkboxes and their descriptions, the three "Not offered" rows, the Owner's "Leave" sentence, the names of the checkboxes, "Always" and "Never" as text, the checkbox saved when made, the text beside it, the refusal returning the box, reset with its confirmation and focus on Cancel), the screen for an Editor and a Viewer (their role and what it may do, no control), and the automated accessibility check of the page.

**Mutations, each tried once on purpose and restored from a saved copy** (named in the pull request): the publish after a change left out; the notice published before the commit; the caller not read again under the lock; the lock dropped; a non-Owner allowed to change; a fixed cell allowed; a "never" cell allowed; the Reviewer column allowed; the cells written one at a time past a refused one; the entry written after the commit; the entry not written for a change; a refusal not logged; the origin not checked first; the cookie cache used; `decide` comparing the role alone; the event not handled; the permissions notice not sent; the set not read again at the next request (a cache); the reset leaving the Reviewer cells of the comment rows; the stored set trusted for a cell that reads "never".
