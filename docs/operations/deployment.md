# What a deployment must do

Provisioning the production services and setting their secrets are the owner's tasks. This page lists what the application's code relies on a deployment to do. Each item is something the code cannot do for itself; a deployment that leaves one out is less safe than the tests show. The page is reviewed on each deployment, with the allow-list of `src/proxy.ts` (NFR-SE-05).

## A reverse proxy stands in front of each process

1. **The web application is reachable only through the proxy.** With `TRUSTED_PROXY_COUNT` set to the number of proxies, the application takes a client's network address from the entry of `X-Forwarded-For` that the outermost of them wrote. A client that reaches the process directly writes that entry itself.
2. **`TRUSTED_PROXY_COUNT` is 1 or more, and a process refuses to start otherwise** wherever `APP_ORIGIN` is not on localhost (the owner's decision of 8 October 2026). The count is the number of proxies between a client and the process, each of which adds one entry to `X-Forwarded-For`: with 1 the application reads the last entry, with 2 the last but one, and so on, so that it reads the entry the outermost proxy wrote and never one a client wrote. A count that is too high reads an entry the client wrote, and lets a client choose its own address; one that is too low reads the address of an inner proxy, and every client shares its count. Next.js 16.4.0 gives `proxy.ts` no address it can trust without a proxy (`next/dist/server/base-server.js`: the header is filled from the socket only where the request carried none). With 0, which is the initial value on localhost and is admitted nowhere else, every request without a session shares one count of NFR-SE-07, and one client can use it up for everyone.
3. **The outermost proxy overwrites `X-Forwarded-For` with the address of its peer**, and each proxy behind it appends the address of its own peer, as a bare IPv4 or IPv6 address. Where there is one proxy it overwrites the header. A proxy that only appends is safe too, as long as the count is exact, since the entries a client wrote stand to the left of those that are read. An entry written with a port, or in brackets, is not read as an address, and such requests share the one count. The setting cannot show that the proxy exists: a process that starts with a count of 1 and is reached directly takes whatever address the client writes.
4. **The proxy removes the header `x-prerender-revalidate` from every request.** Next.js does not pass a request through `proxy.ts` where this header holds the identifier of the build (`next/dist/server/next-server.js`, `runMiddleware`). The identifier is written into the build output (`.next/prerender-manifest.json`). A request that carried it would meet no session check, no origin check, and no limit at the proxy. Each route handler validates the session itself as well (`tests/unit/routes.test.ts`), so such a request to a route handler is still refused where it needs a session; the origin check and the limits are what it would escape. The endpoints that change state without a session (sign-in by password and by the link of a lock email, the second step, the request for a password reset and its completion, and the acceptance of an invitation) check the origin themselves as well and answer as the proxy does, with one entry in the security log for each network address in each period of the limit for a network address (a minute, as it is first set); the limit for each network address is the proxy's alone. That covers route handlers and not pages: a page under the signed-in layout checks the session in its layout from the next slice on, and until then the application's one page shows nothing of an account.
5. **The proxy serves the collaboration server on the application's own origin**, under `/collab`, since the session cookie is host-only (NFR-SE-17 (c)). It sends `/collab` and `/collab/health`, and no other path, to the collaboration server process, and everything else to the web application.
6. **The proxy passes the WebSocket upgrade through** on `/collab`: the `Upgrade` and `Connection` headers, HTTP/1.1 to the process, and the `Origin` and `Cookie` headers exactly as the browser sent them. The collaboration server refuses a handshake whose `Origin` is not `APP_ORIGIN`, character for character, before it reads the cookie (FR-AU-08); a proxy that rewrites or drops `Origin` makes every handshake a 403.
7. **The proxy does not close an idle WebSocket in under a minute.** The server itself ends a connection from which it has received nothing for 60 seconds, and pings each one every 30.
8. **The collaboration server is reachable only through the proxy**, as the web application is (item 1). The header rules of this section apply to it unchanged; it reads no network address, and so no `X-Forwarded-For`.
9. **`COLLAB_PROXY_TARGET` is never set in a deployment.** It is the arrangement of a development machine, which has no reverse proxy: where it is set, the web application itself passes `/collab`, and the WebSocket upgrade with it, to the collaboration server (`next.config.ts`, `collabRewrites`). It would put the collaboration server behind the web application instead of beside it behind the proxy, so it is refused twice. When the application is built, the build fails unless `APP_ORIGIN` and the target are both on localhost (`next.config.ts`). When the web application or the collaboration server starts, the process exits where `APP_ORIGIN` is not on localhost and the setting is present, whatever its value (`src/lib/settings.ts`, `loadSettings`). The second check is needed because `next start` reads its rewrites from the build and never from the environment: a build made with the setting on a development machine serves the rewrite wherever it is started. So the web application also reads `.next/routes-manifest.json` in its working directory when it starts, and exits where `APP_ORIGIN` is not on localhost and that file holds a rewrite of `/collab`, or cannot be read as a manifest (`refuseBuiltCollabRewrite`). What is not checked: the target of a rewrite the build holds, and a build kept anywhere but `.next` under the working directory (`next start <directory>` from elsewhere), where the file is not found and nothing is refused. **Build the artefact of a deployment without the setting.** `APP_ORIGIN` on localhost is itself admitted for a development machine alone. It changes nothing of what the collaboration server checks: the `Origin` and `Cookie` headers reach it as the browser sent them, and it refuses a handshake whose `Origin` is not `APP_ORIGIN` as it does anywhere (FR-AU-08). A handshake that passes through the web application this way also passes through `src/proxy.ts` (Next.js 16.4.0 runs it for an upgrade request: `next/dist/server/lib/router-server.js`, `upgradeHandler`), so one without a session is ended there and may never reach the collaboration server; in a deployment the collaboration server's own check of the session is the only one, and is the one the tests are written against.

## The Content-Security-Policy and the headers beside it

Every response of the web application carries a Content-Security-Policy and three headers beside it (`src/lib/csp.ts`; the owner's decision of 9 October 2026: no inline script, no remote origins, inline style attributes allowed, framing denied). The application sets them itself; a deployment has three things to keep.

- **A page** is answered with this policy, in which the nonce is made for the one request by `src/proxy.ts`, and is on every script of the page:

  ```
  default-src 'self'; script-src 'self' 'nonce-…'; style-src 'self' 'nonce-…'; style-src-attr 'unsafe-inline'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; frame-src 'none'; worker-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests
  ```

  `upgrade-insecure-requests` is left out where `APP_ORIGIN` is on localhost. The development server (`NODE_ENV` is `development`, which `pnpm dev` sets and `pnpm start` never does) adds `'unsafe-eval'` to `script-src` and has `'unsafe-inline'` in place of the nonce in `style-src`, which Next.js 16.4.0 needs there and nowhere else.

- **Everything else** is answered with `default-src 'none'; frame-ancestors 'none'`: the answers of the API routes, the files of the build, every answer the proxy makes itself (a redirect to the sign-in page, a 401, a 403, a 429, a 500), and any response that did not pass the proxy (item 4 above). It is set for every path in `next.config.ts`, and the proxy replaces it on the pages it passes on. So a page that reaches a browser without having passed the proxy runs no script and loads no stylesheet: it is refused whole rather than served without a nonce.
- **Beside it, on every response:** `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: strict-origin-when-cross-origin`, which is `no-referrer` on the pages whose address holds a token, as before.
- **Why inline style attributes are allowed** (`style-src-attr 'unsafe-inline'`): the editor's library writes the widths of a table's columns as `style` attributes, the editor places its toolbar by one, and components of the design package carry them. A `style` attribute cannot load anything under this policy (`img-src` and `font-src` admit this origin alone) and cannot run script. A `<style>` element is admitted only with the nonce; the editor's library writes one.
- **Why `script-src` has no `'strict-dynamic'`**, which the example of Next.js has: under it a browser trusts every script element that a running script makes, from any origin, and ignores `'self'`. Every script of the build is this origin's, so nothing needs it.
- **Every page is rendered for its request.** A nonce cannot be written into a page that was rendered when the application was built, so no page is: `/sign-up`, `/reset-password` and the page of an address that is none were, before this policy. No page may be cached by a proxy or a content delivery network and served to a second request; its nonce would be the first request's.
- **There is no report endpoint**, and the policy names none (`report-uri`, `report-to`). It would be a route without a session that takes bodies an attacker writes. What a browser refuses is seen in that browser's console, and by the end-to-end tests, which fail where any page does anything the policy refuses (`tests/e2e/fixtures.ts`).
- **The collaboration server** answers its health check and every refusal of a handshake with `default-src 'none'; frame-ancestors 'none'` and `X-Content-Type-Options: nosniff`.

What a deployment must do:

10. **The proxy passes these headers through unchanged**: `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options` and `Referrer-Policy`. It does not strip them, does not set a policy of its own in their place, and does not add a second `Content-Security-Policy` header, which a browser would enforce together with the application's and which could not hold the nonce.
11. **The proxy does not cache a page**, and does not rewrite the body of one: a script it added would carry no nonce, and would not run.
12. **`Strict-Transport-Security` is the proxy's to set**, since the proxy ends TLS and knows whether every subdomain is served over it. The application sets none.

## The editor's connection

The page of a document opens one WebSocket to `/collab` on its own origin and keeps it for as long as the page is open (FR-ED-15). What a deployment should expect of it:

- **A lost connection is tried again by the browser** after 1 second, then after twice as long each time, and at least every 30 seconds, with a random part so that the browsers of a restarted server do not return together. After `COLLAB_ERROR_AFTER_MS`, 30000 where unset and at least 1, the page shows the error state and the document is read-only until the connection returns (FR-ED-18, FR-ED-23). The setting is the web application's, which hands it to the page.
- **Each failed attempt is followed by one request to `GET /api/documents/[id]`**, by which the page learns why: a handshake that is refused as a whole is an HTTP status that a browser does not show to a page. A 401 ends the attempts with the statement that the session has ended, and a 404 with the statement that there is no such document for the account. Any other answer, and none, leaves the attempts running. These requests count against the limit of API requests for each user (NFR-SE-07).
- **A refusal that will not change is not tried again**: no access, access ended, and session ended (FR-ED-41). A document at its limit of connections is tried every 30 seconds (FR-ED-18), and a refusal for the limit of handshakes after 5 seconds, then twice as long each time, up to a minute.
- **A proxy that answers the upgrade itself where the collaboration server is down** (a 502 or a 503) is read as a lost connection, as it should be.

## The collaboration server

It is a process of its own, `pnpm start:collab`, with the same settings as the web application: both read `src/lib/settings.ts`, and `FOUNDING_TEAM_EMAILS`, `APP_ORIGIN`, `DATABASE_URL`, `VALKEY_URL` and `AUTH_SECRET` must be the same for the two, or a session of one is no session of the other (NFR-SE-17 (f)). `COLLAB_PORT` is the port it listens on, 1234 where unset.

**A deployment stops it with `SIGTERM` and waits for it to exit.** On `SIGTERM` or `SIGINT` it accepts no further handshake, stores every open document, and exits with 0; it exits with 1 where a document could not be stored after three attempts, and at once on a second signal (NFR-RE-07). A process that is killed stores nothing: what it had received in the 2 seconds before (`COLLAB_STORE_DELAY_MS`), or in the 10 seconds before while changes kept arriving (`COLLAB_STORE_MAX_MS`), is held only by the browsers that sent it, which send it again when they reconnect.

**One instance only, for now.** Two instances do not yet share a document: each would hold its own copy and store over the other's (NFR-SC-04 is not built). And a connection that was accepted stays open until its browser closes it: the server does not yet end it when the session ends or when the account loses its role (of NFR-SE-03 (b) to (e), only the deletion of a document is built). Both are later slices of the plan.

**It hears of a deleted document over Valkey, and listens only once it does.** The web application publishes the deletion of a document on the Valkey channel `ekdotico:collab-events`, and every collaboration server instance that hears it reads the document's row, stores what it had received for the document and not yet stored, and closes its connections to it (FR-ED-40 (c), FR-ED-41, NFR-SE-03 (d); `src/lib/collab/events.ts`). So the two processes must share one Valkey, and a collaboration server that cannot subscribe at start does not open its port, and its health check does not answer, until it can. A notice that is lost, because Valkey was away for a moment, leaves a connection open: the re-check that closes it within 60 seconds (FR-ED-41) is a later slice.

**The Valkey user of the collaboration server must be allowed to subscribe to that channel, and the user of the web application to publish on it.** A managed Valkey with access control lists refuses a channel that the user's list does not name. A collaboration server that is refused prints one line on stderr, `collab events: not subscribed (ReplyError NOPERM)`, with the code word of Valkey's reply (`NOAUTH` where the password is missing or wrong), and asks again after 1 second, then after twice as long each time, and at least every 30 seconds. It prints no further line while the fault stays the same, and `collab events: subscribed again` once it is subscribed. Until then, at start, its port stays closed and it does not exit: a port that never opens, with that one line, is this fault.

**The health check of the collaboration server shows that the process is up, listening, and subscribed to that channel, and nothing else.** `GET /collab/health` answers 200 with an empty body while the process is subscribed, and 503 with an empty body and `Cache-Control: no-store` from the moment it loses its connection to Valkey for the channel until it is subscribed again (the owner's decision of 8 October 2026, which amends choice C20 of the plan for this one case; NFR-SE-05 (c)). It checks no other dependency: not the database, and not whether Valkey answers a command. The check changes only what it answers. A server that answers 503 still admits handshakes for as long as it can reach Valkey for the limits, keeps the connections it holds, and does not hear of a deleted document until it is subscribed again; the two lines above, on stderr, say why. The health check of the web application is unchanged, and checks no dependency.

A notice is never obeyed for what it says. Anything that can reach Valkey can publish one, so the collaboration server closes the connections to a document only where the document's row says it is deleted, or is gone. The Valkey of the application is reachable by the two processes alone.

## Deleted documents

A deleted document is kept for `DELETED_DOCUMENT_RETENTION_DAYS`, 30 where unset, at least 1 and at most 3650, and is then deleted permanently, with its state, by a timer in the web application that runs at start and each hour (FR-ED-36, NFR-RE-15). Any number of instances may run it: each document is claimed by one of them.

**Lowering `DELETED_DOCUMENT_RETENTION_DAYS` applies to the documents that are already deleted.** The end of a retention is not stored with the document: each run works it out from the moment of the deletion and the setting as it then is. At the first run after the setting is lowered, every document deleted longer ago than the new value is deleted permanently, although its Owner was shown the date the old value gave. Raising it gives every deleted document the longer time.

**The instances agree on the setting and on the time.** Each instance judges a retention, and the age of another instance's unfinished claim, by its own clock and its own setting, against times that the other instances wrote. Every instance of the web application is given the same `DELETED_DOCUMENT_RETENTION_DAYS`, and their clocks are kept together, as a time service keeps them: an instance whose clock runs ahead deletes that much early.

The lines of this work, on stderr, each name the document by its identifier and never by its title (NFR-SE-19):

- `permanent deletion: document <id> kept (…)`: the document could not be deleted in that run, and is tried again in the next. In the brackets, `Istorico did not erase`, or the class and code of a fault.
- `collab events: document-deleted not published for document <id> (…)`: the document is deleted, and the collaboration servers were not told. Its open connections stay open until their browsers close them.
- `collab events: document-deleted not handled for document <id> (…)` and `collab: document <id> not read for a notice (…)`: a collaboration server was told and could not act, or could not read the row. In the second case it closes the connections to the document as unavailable, and each browser connects again.
- `collab: last store of document <id> failed (…)`: a collaboration server could not store what it had received for the document before closing its connections. They are closed all the same. What is lost is what that server had received since its last store, at most the 2 or 10 seconds of `COLLAB_STORE_DELAY_MS` and `COLLAB_STORE_MAX_MS`; the state stored before stays, and is what a restore returns.

## The build output is kept as a secret is

The `.next` directory holds the identifier of item 4. A container image, a build artefact, and a host that hold it are readable only by those who may deploy. Draft mode is never used, since it sends the same identifier to the browser as a cookie; the lint rule in `eslint.config.mjs` refuses its import.

## Settings

A process refuses to start without `FOUNDING_TEAM_EMAILS`, `APP_ORIGIN`, `DATABASE_URL`, `VALKEY_URL`, and `AUTH_SECRET`, and, away from a development machine, without `EMAIL_TRANSPORT`, `EMAIL_SINK_DIRECTORY`, and a `TRUSTED_PROXY_COUNT` of 1 or more. `.env.example` describes each. No variable whose name begins `BETTER_AUTH_` may be set: the identity library reads several of its own, which would change its configuration, and each of the two processes refuses to start where one is present. A variable whose name begins `RATE_LIMIT_` and names no limit stops a process in the same way, as does a period or a length that is 0 or out of order.

An entry of `FOUNDING_TEAM_EMAILS` that is not an email address an account can have stops a process too (the owner's decision of 9 October 2026): an entry with no domain, or with a domain written in full-width or other compatibility letters, or with a label that begins or ends with a hyphen. Such an entry would match no account, and the account it was meant for would not be required to use two-factor authentication. The message gives the position of the entry in the list and never the entry.

`EMAIL_SINK_DIRECTORY` names the directory the email sink writes to. Each file in it holds an address and may hold a single-use link, so a deployment says where they go: only on a development machine is a directory under the working directory used where the setting is absent.

`TWO_FACTOR_STEP_SECONDS` is how long the second step of a sign-in stays open after the password, and how long the secret of an enrolment waits for its first code: 600, the 10 minutes of FR-AU-83, where the setting is absent. `TWO_FACTOR_WRONG_CODES` is the number of wrong codes at which either is over and begins again with the password: 5 where the setting is absent (NFR-SE-07). Each is a whole number, 1 or more, and anything else stops a process.

`SIGN_IN_LOCK_SECONDS` is how long the twentieth failed sign-in for an email address locks its account, and how long the sign-in link in the email of the lock is valid: 3600, the 1 hour of FR-AU-81, where the setting is absent. The twenty and the hour they are counted in are the limit `RATE_LIMIT_FAILED_SIGN_IN_PER_EMAIL`. The email of the lock states all three as they are set. A process refuses to start where `SIGN_IN_LOCK_SECONDS` is less than the seconds of that limit: the failures that caused a lock would still be counted when it ended, and each single failure after it would lock the account again and send its email. The lock is the column `User.lockedUntil`, so it holds on every instance; a sign-in reads it once, and is refused where the database does not answer.

Three ceilings of the lock and its link are accepted as they are. The count of the five codes that a sign-in link is given in all is kept in Valkey alone, so a link whose count Valkey loses within the hour of the lock is given five more. Where Valkey fails while the counts are cleared after a sign-in by the link, the sign-in stands and the count for the address stays at its number, so until those failures leave their hour the next lock takes one failure and not twenty. And the lock runs on the clock of the application's instance while the counts run on Valkey's: this matters only with more than one instance and clocks that differ, where a lock ends on one instance that much before another. Should it come to matter, the three conditional statements that compare a time (`src/lib/auth/sign-in-lock.ts`) take the database's `now()` instead.

The database client gives up on a connection after 5 seconds, the server ends a statement after 5 seconds, and the client stops waiting for an answer after 5 seconds (`src/lib/db.ts`; NFR-SE-06). A connection to Valkey and a command sent to it are given 5 seconds each (`src/lib/valkey.ts`). A request that meets either fault is refused and never passed on.

Changing `AUTH_SECRET` ends every session and forgets every count of NFR-SE-07, since the counters are stored under digests keyed by it. The procedure for rotating each secret is recorded before the first test user is admitted (NFR-SE-17 (e)); it is not yet written.

## Before a deployment that holds accounts created under an earlier rule

A one-off check, which the owner decided on 9 October 2026. An address is stored in its one spelling and under the one rule of an address (`src/lib/field-text.ts`; FR-AU-02): composed, in lower case, with one sigma, and with a domain that is plain or is a Unicode label that normalisation leaves as it is. An account created before that rule, or before a later change to it, may hold an address that the rule now spells otherwise or refuses. Such an account may be one that no sign-in finds, one that the list of the founding team does not match, or one beside which the same person is given a second account.

1. **Before the first deployment to a database that holds accounts created under an earlier spelling or rule of an address, run the check, with the settings of that deployment:** `node --env-file=<the file of settings> scripts/check-addresses.ts`. It reads the identifier and the address of every account and changes nothing. It prints one line, `address check: <n> of <m> accounts hold an address that is not in its one spelling or that the rule of an address refuses`, and then the identifier of each such account on a line of its own. It never prints an address (NFR-SE-19). It exits with 0 where there is no such account, with 1 where there is one or more, and with 2 where it could not run, in which case the line says `address check: not run`.
2. **Where it names an account, the deployment waits, and the identifiers are reported to the owner.** No row is migrated silently, by the check or by hand. The owner decides for each account what becomes of it: an address rewritten to its one spelling could be the address of another account, and a person signs in with the address as they know it.
3. **The check is run again after whatever the owner decides is done, and the deployment goes ahead when it exits with 0.** The result is recorded with the deployment.

## The password list

`PASSWORD_LIST_FILE` names the list of commonly used and known-compromised passwords (FR-AU-82), by default `data/common-passwords.txt` under the directory the process is started in. The file ships with the deployment. Where it cannot be read, or holds no entry, every request that sets a password fails, so that none is set unchecked. The file in the repository is a published list of 476,776 passwords of 8 to 32 characters (the owner's decision of 8 October 2026; register A66, D86); its name, version, source, licence, and filter, and what loading it costs, are in `data/common-passwords.md`. It is read at the first password that is checked, and then holds about 27 MB of memory.

## Email

The only sender built so far writes each message to a file and sends nothing (register D70 (the three checks stand), D92). A deployment that sets `EMAIL_TRANSPORT=sink` sends no invitation, no reset link, and no notice.
