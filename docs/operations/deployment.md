# What a deployment must do

Provisioning the production services and setting their secrets are the owner's tasks. This page lists what the application's code relies on a deployment to do. Each item is something the code cannot do for itself; a deployment that leaves one out is less safe than the tests show. The page is reviewed on each deployment, with the allow-list of `src/proxy.ts` (NFR-SE-05).

## A reverse proxy stands in front of each process

1. **The web application is reachable only through the proxy.** With `TRUSTED_PROXY_COUNT` set to the number of proxies, the application takes a client's network address from the entry of `X-Forwarded-For` that the outermost of them wrote. A client that reaches the process directly writes that entry itself.
2. **`TRUSTED_PROXY_COUNT` is 1 or more, and a process refuses to start otherwise** wherever `APP_ORIGIN` is not on localhost (the owner's decision of 8 October 2026). The count is the number of proxies between a client and the process, each of which adds one entry to `X-Forwarded-For`: with 1 the application reads the last entry, with 2 the last but one, and so on, so that it reads the entry the outermost proxy wrote and never one a client wrote. A count that is too high reads an entry the client wrote, and lets a client choose its own address; one that is too low reads the address of an inner proxy, and every client shares its count. Next.js 16.4.0 gives `proxy.ts` no address it can trust without a proxy (`next/dist/server/base-server.js`: the header is filled from the socket only where the request carried none). With 0, which is the initial value on localhost and is admitted nowhere else, every request without a session shares one count of NFR-SE-07, and one client can use it up for everyone.
3. **The outermost proxy overwrites `X-Forwarded-For` with the address of its peer**, and each proxy behind it appends the address of its own peer, as a bare IPv4 or IPv6 address. Where there is one proxy it overwrites the header. A proxy that only appends is safe too, as long as the count is exact, since the entries a client wrote stand to the left of those that are read. An entry written with a port, or in brackets, is not read as an address, and such requests share the one count. The setting cannot show that the proxy exists: a process that starts with a count of 1 and is reached directly takes whatever address the client writes.
4. **The proxy removes the header `x-prerender-revalidate` from every request.** Next.js does not pass a request through `proxy.ts` where this header holds the identifier of the build (`next/dist/server/next-server.js`, `runMiddleware`). The identifier is written into the build output (`.next/prerender-manifest.json`). A request that carried it would meet no session check, no origin check, and no limit at the proxy. Each route handler validates the session itself as well (`tests/unit/routes.test.ts`), so such a request to a route handler is still refused where it needs a session; the limits are what it would escape. Every route handler that changes state checks the origin itself as well (`tests/unit/route-origin.test.ts`; the owner's decision R50 of 12 October 2026), before it looks at the session, and answers as the proxy does: the endpoints of the identity handler, the acceptance of an invitation, the creation, renaming, deletion and restoring of a document, the invitations and their answers, the change of a role, the removal of a collaborator, leaving a document, and the acknowledgement of the notice. The signed admission endpoints alone do not: they carry no cookie and are authenticated by their signature. A refusal made by a route has one entry in the security log for each network address in each period of the limit for a network address (a minute, as it is first set); the limit for each network address is the proxy's alone. That covers route handlers and not pages: a page under the signed-in layout checks the session in its layout from the next slice on, and until then the application's one page shows nothing of an account.
5. **The proxy serves the collaboration server on the application's own origin**, under `/collab`, since the session cookie is host-only (NFR-SE-17 (c)). It sends `/collab` and `/collab/health`, and no other path, to the collaboration server process, and everything else to the web application.
6. **The proxy passes the WebSocket upgrade through** on `/collab`: the `Upgrade` and `Connection` headers, HTTP/1.1 to the process, and the `Origin` and `Cookie` headers exactly as the browser sent them. The collaboration server refuses a handshake whose `Origin` is not `APP_ORIGIN`, character for character, before it reads the cookie (FR-AU-08); a proxy that rewrites or drops `Origin` makes every handshake a 403.
7. **The proxy does not close an idle WebSocket in under a minute.** The server itself ends a connection from which it has received nothing for 60 seconds, and pings each one every 30.
8. **The collaboration server is reachable only through the proxy**, as the web application is (item 1). The header rules of this section apply to it unchanged; it reads no network address, and so no `X-Forwarded-For`.
9. **`COLLAB_PROXY_TARGET` is never set in a deployment.** It is the arrangement of a development machine, which has no reverse proxy: where it is set, the web application itself passes `/collab`, and the WebSocket upgrade with it, to the collaboration server (`next.config.ts`, `collabRewrites`). It would put the collaboration server behind the web application instead of beside it behind the proxy, so it is refused twice. When the application is built, the build fails unless `APP_ORIGIN` and the target are both on localhost (`next.config.ts`). When the web application or the collaboration server starts, the process exits where `APP_ORIGIN` is not on localhost and the setting is present, whatever its value (`src/lib/settings.ts`, `loadSettings`). The second check is needed because `next start` reads its rewrites from the build and never from the environment: a build made with the setting on a development machine serves the rewrite wherever it is started. So the web application also reads `.next/routes-manifest.json` in its working directory when it starts, and exits where `APP_ORIGIN` is not on localhost and that file holds a rewrite of `/collab`, cannot be read as a manifest, or is not there (`refuseBuiltCollabRewrite`): a build that cannot be checked does not pass. So a deployment starts the web application in the directory that holds `.next`; a build kept elsewhere (`next start <directory>` from another directory) is refused, because its manifest is not found. What is not checked: the target of a rewrite the build holds. **Build the artefact of a deployment without the setting.** `APP_ORIGIN` on localhost is itself admitted for a development machine alone. It changes nothing of what the collaboration server checks: the `Origin` and `Cookie` headers reach it as the browser sent them, and it refuses a handshake whose `Origin` is not `APP_ORIGIN` as it does anywhere (FR-AU-08). A handshake that passes through the web application this way also passes through `src/proxy.ts` (Next.js 16.4.0 runs it for an upgrade request: `next/dist/server/lib/router-server.js`, `upgradeHandler`), so one without a session is ended there and may never reach the collaboration server; in a deployment the collaboration server's own check of the session is the only one, and is the one the tests are written against.

## The Content-Security-Policy and the headers beside it

Every response of the web application carries a Content-Security-Policy and six headers beside it (`src/lib/csp.ts`; the owner's decisions of 9 October 2026: no inline script, no remote origins, inline style attributes allowed, framing denied; and, on the second review of pull request 20, the three that keep a response to its own origin). The application sets them itself; a deployment has three things to keep.

- **A page** is answered with this policy, in which the nonce is made for the one request by `src/proxy.ts`, and is on every script of the page:

  ```
  default-src 'self'; script-src 'self' 'nonce-…'; style-src 'self' 'nonce-…'; style-src-attr 'unsafe-inline'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; frame-src 'none'; worker-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests
  ```

  `img-src` names one origin more where the application has an object store for images (`IMAGE_STORAGE_*`), and then reads `img-src 'self' https://<bucket>.fra1.digitaloceanspaces.com` (the owner's decision of 20 October 2026, S19-4; src/lib/settings.ts derives it from the endpoint and the bucket, and `exactOrigin` of `src/lib/csp.ts` refuses anything that is not an origin: no wildcard, scheme, path or list). It is the origin the links of an image are signed for, it is the only one, and no other directive names it. Where no store is set the policy is the one above. `upgrade-insecure-requests` is left out where `APP_ORIGIN` is on localhost. The development server (`NODE_ENV` is `development`, which `pnpm dev` sets and `pnpm start` never does) adds `'unsafe-eval'` to `script-src` and has `'unsafe-inline'` in place of the nonce in `style-src`, which Next.js 16.4.0 needs there and nowhere else.

- **Everything else** is answered with `default-src 'none'; frame-ancestors 'none'`: the answers of the API routes, the files of the build, every answer the proxy makes itself (a redirect to the sign-in page, a 401, a 403, a 429, a 500), and any response that did not pass the proxy (item 4 above). It is set for every path in `next.config.ts`, and the proxy replaces it on the pages it passes on. So a page that reaches a browser without having passed the proxy runs no script and loads no stylesheet: it is refused whole rather than served without a nonce.
- **Beside it, on every response:** `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: strict-origin-when-cross-origin`, which is `no-referrer` on the pages whose address holds a token, as before. And `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, and a `Permissions-Policy` that grants one feature of the browser, `clipboard-write=(self)`, which the two buttons that copy use, and refuses every other it names to every origin, this one included: the camera, the microphone, the location, reading the clipboard, payment, USB and the rest of the list in `src/lib/csp.ts`. A page of the application therefore cannot read the clipboard; a feature a later slice needs is added to that list when the slice is built.
- **Why inline style attributes are allowed** (`style-src-attr 'unsafe-inline'`): the editor's library writes the widths of a table's columns as `style` attributes, the editor places its toolbar by one, and components of the design package carry them. A `style` attribute cannot load anything under this policy (`img-src` and `font-src` admit this origin alone) and cannot run script. A `<style>` element is admitted only with the nonce; the editor's library writes one.
- **Why `script-src` has no `'strict-dynamic'`**, which the example of Next.js has: under it a browser trusts every script element that a running script makes, from any origin, and ignores `'self'`. Every script of the build is this origin's, so nothing needs it.
- **Every page is rendered for its request.** A nonce cannot be written into a page that was rendered when the application was built, so no page is: `/sign-up`, `/reset-password` and the page of an address that is none were, before this policy. No page may be cached by a proxy or a content delivery network and served to a second request; its nonce would be the first request's.
- **There is no report endpoint**, and the policy names none (`report-uri`, `report-to`). It would be a route without a session that takes bodies an attacker writes. What a browser refuses is seen in that browser's console, and by the end-to-end tests, which fail where any page does anything the policy refuses (`tests/e2e/fixtures.ts`).
- **The collaboration server** answers its health check and every refusal of a handshake with `default-src 'none'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, and the same `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` and `Permissions-Policy`.

What a deployment must do:

10. **The proxy passes these headers through unchanged**: `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` and `Permissions-Policy`. It does not strip them, does not set a policy of its own in their place, and does not add a second `Content-Security-Policy` header, which a browser would enforce together with the application's and which could not hold the nonce.
11. **The proxy does not cache a page**, and does not rewrite the body of one: a script it added would carry no nonce, and would not run.
12. **`Strict-Transport-Security` is the proxy's to set**, since the proxy ends TLS and knows whether every subdomain is served over it. The application sets none.

## The editor's connection

The page of a document opens one WebSocket to `/collab` on its own origin and keeps it for as long as the page is open (FR-ED-15). What a deployment should expect of it:

- **A lost connection is tried again by the browser** after 1 second, then after twice as long each time, and at least every 30 seconds, with a random part so that the browsers of a restarted server do not return together. After `COLLAB_ERROR_AFTER_MS`, 30000 where unset and at least 1, the page shows the error state and the document is read-only until the connection returns (FR-ED-18, FR-ED-23). The setting is the web application's, which hands it to the page.
- **Each failed attempt is followed by one request to `GET /api/documents/[id]`**, by which the page learns why: a handshake that is refused as a whole is an HTTP status that a browser does not show to a page. A 401 ends the attempts with the statement that the session has ended, and a 404 with the statement that there is no such document for the account. Any other answer, and none, leaves the attempts running. These requests count against the limit of API requests for each user (NFR-SE-07).
- **A refusal that will not change is not tried again**: no access, access ended, and session ended (FR-ED-41). A document at its limit of connections is tried every 30 seconds (FR-ED-18), and a refusal for the limit of handshakes after 5 seconds, then twice as long each time, up to a minute. A connection that was closed for the limit of messages (below) is asked for again after 5 seconds, on the same socket.
- **A proxy that answers the upgrade itself where the collaboration server is down** (a 502 or a 503) is read as a lost connection, as it should be.

## The collaboration server

It is a process of its own, `pnpm start:collab`, with the same settings as the web application: both read `src/lib/settings.ts`, and `FOUNDING_TEAM_EMAILS`, `APP_ORIGIN`, `DATABASE_URL`, `VALKEY_URL` and `AUTH_SECRET` must be the same for the two, or a session of one is no session of the other (NFR-SE-17 (f)). `COLLAB_PORT` is the port it listens on, 1234 where unset.

**A deployment stops it with `SIGTERM` and waits for it to exit.** On `SIGTERM` or `SIGINT` it accepts no further handshake, stores every open document, and exits with 0; it exits with 1 where a document could not be stored after three attempts, and at once on a second signal (NFR-RE-07). A process that is killed stores nothing: what it had received in the 2 seconds before (`COLLAB_STORE_DELAY_MS`), or in the 10 seconds before while changes kept arriving (`COLLAB_STORE_MAX_MS`), is held only by the browsers that sent it, which send it again when they reconnect.

**A document has two limits, which the collaboration server holds every update to** (`src/lib/collab/state.ts`; the owner's decision of 9 October 2026): its state, encoded as it is stored, is at most 5 MB (5 × 1024 × 1024 bytes), and its elements are nested at most 50 deep, counted from an element that stands directly in the document to the innermost. A list of ten levels is 21 deep, and 26 inside a quote inside a cell of a table; the deepest list there is room for has 24 levels. An update that would take a document past either is not applied, not stored, and sent to no one: the connection that sent it is closed with a reason that names the limit (`too-large` or `too-deep`, and `too-dangling` for the bound on what a document waits with, below; `src/lib/collab/protocol.ts`), and one entry of the kind `document_limit_refused` is written to the security log, with the user and the document (the owner's decisions of 12 October 2026). The page that sent it does not send it again: it keeps the text, read-only, states which limit the change would pass, and offers to copy the text before the document is reloaded, which discards the change. A document stored before there were limits, and past one, still opens, and takes every change that does not take it further past. The socket itself takes no message longer than 5 MB and 64 KB (`maxPayload`; the socket library's own bound is 100 MiB) and closes with the code 1009 on one that is; **a proxy in front of it must allow WebSocket messages of that length**; the page that sent such a message says the same as for the limit of size. An update is tested against a copy of the document only when it must be: the server keeps, for each document in memory, a number of bytes and a depth that the document is not past, adds what each update can add at most, and copies the document when the sum would pass a limit and at the first update after a load. A document that waits for a change it has not been sent is not copied for every update: what waits is counted in advance, as a keeper charges it (`owedBy`, `src/lib/collab/state.ts`), so that its bytes, and what taking it in can add, are in the sum at every measure, and its levels are added for an update that holds a change of the client it waits for (commit `24520d6`). **What a document may wait with is bounded** (`MAX_WAITING_PARTS` in `src/lib/collab/state.ts`, not a setting; the owner's decision of 12 October 2026): at most 2,000 parts, the structs and the deleted ranges that name content the document was never sent. The update that would take it past is refused as one that passes a limit of size is, and written to the security log as `document_limit_refused`, once in each period for a document and a user. Without the bound one update of some 18 KB with thousands of structs filled the room that the cheap answer needs, and every later update of every member was a copy of 443 to 599 ms. The server keeps a count that is never less than the parts that wait: it adds every part of each update it lets through, whether the update waits or is taken in, and counts again, exactly, by a copy, when the sum would pass 2,000, which is once in 1,000 to 2,000 updates of a document that waits for nothing; that copy is 65 ms to 250 ms for a document of 4.9 MB, and a few milliseconds for a document of ordinary size. A document that waits with more already, stored before the bound, still opens and takes every update that adds no part to what waits (each of them is measured, as before), and refuses one that adds; a document that sits within a few parts of 2,000 makes every update with more parts than the room left a copy, which the limit of messages below bounds. The refusal has a reason of its own, `too-dangling`, and the page says "A change in this tab refers to content that this document does not hold, so it cannot be applied", with the rest of the statement as for the other two limits: the text stays, read-only, there is no new try, and the writer is offered to copy the text before the document is reloaded (the owner's decision of 12 October 2026; the words are under the Expression Guidelines, for the owner's approval). A copy takes 65 ms for 4.9 MB of prose and 250 ms for 4.9 MB of the smallest pieces (measured 12 October 2026). A member who fills a document to within a few bytes of its limit makes every update a copy again, which the limit of messages below bounds.

**The collaboration server holds the shape of a document as well** (`src/lib/collab/shape.ts`; register D170, D171, D172, D180). An update inside the limits is refused, in the same way and with the same entry in the security log, where it creates an element without the content the editor's schema requires of it (`incomplete`: a table without a row, a cell without a paragraph), or takes a table past a bound (`table-bounds`: 100 rows, 100 cells in a row, 10,000 cells in a table and the tables in its cells together, two levels of table). An update that empties an element that is there already is not refused. A table stored past a bound is refused only what takes it further past. The check reads the update and the elements it names, and copies the document only for an update that Yjs would not take in whole and at once, which no browser sends while it writes: a key typed is answered in under 0.01 ms, and a row of 100 cells in a full table in about 6 ms, where the copy takes about 40 ms at 4.6 MB (measured 16 October 2026).

**A user may send a collaboration server 600 messages that carry an update in any minute** (`RATE_LIMIT_COLLAB_MESSAGES_PER_USER`, written `max/seconds`; the owner's decision of 12 October 2026, a row to be added to NFR-SE-07). The message past the limit is not read, not applied, and costs no check of the document's limits: the connection that sent it is closed with the reason `limited`, and one entry of the kind `rate_limit_reached` is written to the security log for the user in each period of the limit, however many connections are closed in it. What is counted is the second step of a synchronisation and an update, on every connection of the user to that server together, a connection that cannot edit included; awareness (a cursor) and the first step of a synchronisation are not counted.

- **The count is the user's and not the connection's.** A count on the connection begins again with the next connection, and the limit of handshakes lets a user open 30 more each minute and keep them: after ten minutes one account could send 300 times the limit.
- **The count is in the memory of the instance, the one limit that is not in Valkey.** What it protects is the single thread of that instance, which no other instance shares, so each instance holds its own 600 for a user. And it is asked for every key a writer presses: a count in Valkey took 0.15 ms at the median and 0.4 ms at the 99th percentile on one machine (the check of a document's limits itself takes 0.004 ms, and the count in memory 0.0001 ms; measured 12 October 2026), every change would wait for that answer before it was applied, and a Valkey that did not answer would refuse every change of every writer. A restart of the instance begins every count again.
- **What the limit leaves.** 600 copies in a minute are 39 seconds of the instance's thread for a document of 4.9 MB of prose (65 ms each), and more than the whole minute for one of the smallest pieces (250 ms each): one account that fills a document to its limit can still slow an instance for everyone on it, and cannot do more than that. The security log names the account, once a minute.
- **What a writer sends** (`src/lib/collab/client.ts`; the owner's decision of 12 October 2026). The editor sends a change at once while a bucket of 8 messages holds one, and merges the changes that come when it does not into one message, sent 250 ms after the first of them (the provider's `flushDelay`, `@hocuspocus/provider` 4.7.0). A message costs one, and one returns every 250 ms. A paste is one message, of 4 MB too (measured in Chromium, `tests/e2e/editor.spec.ts`). Typing is therefore sent as it is made, and keeps the budget for a change to reach a collaborator in SRS §2.4 (a median under 150 ms, 99 in 100 under 400 ms): on the loopback of one machine, which has no network, a single keystroke reached another client in a median of 3 ms (20 keystrokes, 12 October 2026; the budget is for a connection to Frankfurt, which is not measured here). Only fast typing for some seconds reaches the bucket: more than 4 keys a second for long enough to empty it, which is then 4 messages a second, and a change waits 250 ms at most.
- **What a key held down comes to.** It repeats some 10 to 30 times a second by the settings of the operating system. It is sent as 8 messages at once and then 4 a second for as long as it is held (853 repeats in 30 seconds were 127 messages; measured 12 October 2026). In any period of L seconds a tab sends at most 8 + 4 L update messages, whatever the keys do: 248 in a minute, and 496 for two tabs of one account, under the 600. The two steps of a synchronisation that a connection sends when it opens are charged to the bucket, and come on top. The page shows "In sync" and "Syncing" in turn, "Syncing" for each message from its sending to its acknowledgement; it does not show the connection as being restored or lost. A change that only waits for its batch is not counted as unsent while the connection is up, so the words that changes are lost if the tab is closed are shown for a message sent and not yet acknowledged, or when the connection is lost, and not at every pause in typing.
- **A page that is hidden or left sends what waits, at once.** On `pagehide`, on `visibilitychange` to hidden, and when the connection is stopped (the page of a document is left), the batch is sent as one message, outside the bucket. Nothing written before the tab is closed is held back for its 250 ms. A tab that is killed, or whose browser stops, sends nothing: the browser's last words are the events above, and the network may still drop the message of a page that is gone (not tested). The check of the sync status (FR-ED-24) sends what waits before it asks.
- **Where the limit is reached all the same** (three tabs of one account held at once, or a client that is not the editor), the page shows the connection as being restored, keeps the changes in the tab, asks for the document again after 5 seconds, and then sends what the server lacks as one message; while the minute is still full that message is refused in the same way, and the page waits 5 seconds again. Nothing written is lost. What is typed during the 5 seconds is sent by the same bucket, so at most 8 + 4 a second reach a server that has no connection to the document. The server keeps such messages for the socket (the library's bound, `@hocuspocus/server` 4.7.0: 1,000 messages or 5 MB for all the documents of a socket that are not open; past either it closes the socket, which the browser opens again as a lost connection) and hands them to the connection when the document is opened again: each is then counted against the limit and applied, before the one message with what the server lacks.

**A document holds at most ten connections** (`CONNECTIONS_PER_DOCUMENT` of `src/lib/collab/presence.ts`; NFR-PE-05, FR-ED-18; register D174). Each connection counts, whatever the role, and one account's two tabs are two. The eleventh is refused with the reason `capacity` after the authorisation, so that an account with no role is told nothing of how full a document is, and before any state of the document is sent; the page shows the fixed statement and asks again every 30 seconds. The place is taken in one synchronous step with the count, so that handshakes that arrive together cannot pass the limit between them, and is given back the moment the connection closes. A place whose connection was never made (a socket that closed in the middle of the handshake, a load that failed where nothing could give it back) stops counting after 15 seconds. A client that goes away without closing its socket keeps its place until the library's ping notices, within 30 seconds, and a client that reconnects at once can meet the limit as `capacity` and tries again. **The count is in the memory of the instance**, so two instances would each admit ten: the shared count belongs to the release that adds an instance (register Q42, D174). The limit is a constant and not a setting, because the fixed statement says "ten" and the colour set of `@ekdotico/domico` holds ten colours (FR-ED-17); the owner revisits the two together (register Q31).

**What a connection may say of itself is its cursor, under the name and the colour the server holds for it** (`src/lib/collab/presence.ts`; FR-ED-17). The library relays awareness from a connection of any role, a read-only one too, to every other: the server rebuilds each state as `{ user: { name, slot }, cursor }`, where the name is the account's (or the part of its address before the `@`), read when the connection was made, and the slot is the lowest of the colour set that no other connection of the document holds. A client speaks for the one identifier it has spoken with, and cannot speak for another's; its cursor is kept only where it is two relative positions as Yjs writes them, since another kind makes the editor of every peer throw; and awareness longer than 4,096 bytes closes the connection before it is read. **Awareness is not rate-limited** (register row S14-5): a cursor sends a message at every move, and only the size of a message and the ten connections bound what it costs. A name changed in the account's settings is shown from the next connection.

**Every open connection is re-checked every 60 seconds** (FR-ED-41; `COLLAB_RECHECK_MS`, 60000 where unset and from 1000 to 60000; `recheck` of `src/collab/server.ts`). One query reads the rows of the sessions the connections were opened under, with the account's address, and `authorise` is asked once for each user and document. A connection whose session has no row, has expired under either period of FR-AU-84, or belongs to a deleted account is closed `session-ended`; one whose role is gone or whose document is deleted, `access-ended`; one whose role changed stays open and is made read-only or editable in place, and told by a stateless message that the editor reads (FR-ED-40 (b)), after the messages it has already received have been handled, for at most 1 second (`PENDING_WAIT_MS`: at that bound a downgrade is made all the same and an upgrade waits for the next look; docs/plan/presence-row.md, 2.3). The identity library, which answers from the signed copy in a cookie, is never asked. A reading that fails closes the connections it was for as `unavailable`, so that each handshake reads the row again (register row S14-3); a run that has not ended when the next is due makes the next wait, so a slow database does not pile runs up. It does not yet read the notice period of a clearing (FR-ED-40 (i)) or the export lock (FR-ED-40 (f)): the columns arrive with those slices. The cost is one query for the sessions and one for each distinct pair of user and document, one after another, each minute.

**One instance only, for now.** Two instances do not yet share a document: each would hold its own copy and store over the other's, and each would count ten connections (NFR-SC-04 is not built; D168, D174). The events of FR-ED-40 that are built are published on the channel below: the deletion of a document, the removal of a collaborator, a leave, a change of role, a change of a document's permission set (`permission-set-changed`, FR-ED-40 (g)), and the end of a session by sign-out, revocation, or a change of the password or the address. A session that ends by expiry is reached by the re-check alone, within 60 seconds. The events (f), (h) and (i) are built with their slices.

**It hears of a change over Valkey, and listens only once it does.** The web application publishes each change on the Valkey channel `ekdotico:collab-events` (the name is the environment variable `COLLAB_EVENTS_CHANNEL` where one is set, which only the tests do, so that runs on one machine do not hear each other), after its commit, and every collaboration server instance that hears it acts within 5 seconds (FR-ED-40, FR-ED-41, NFR-SE-03 (b) to (d); `src/lib/collab/events.ts`). For a deleted document it reads the document's row, stores what it had received for the document and not yet stored, and closes its connections to it. For a removal, a leave, a change of role, and the end of a session it looks at the open connections the message names, by the same readings and the same decision as the re-check (`look` of `src/collab/server.ts`): each read is bounded at 2 seconds and the sessions are read once; a connection whose access or session is gone is closed, one whose role changed is made read-only or editable in place, and where a reading fails the connections it was for are closed `unavailable` and each browser connects again. For a change of a document's permission set it looks at every open connection to the document: the record of each connection is built again from the stored set (`holds`), and one whose role holds other permissions than before keeps its connection, open and as editable as it was, and is told by a stateless message of its own kind that the editor states (FR-ED-40 (g)). Messages that arrive while a look runs are looked at together by the next, and past 1,000 of them the next look is the whole re-check, so a flood costs one look. So the two processes must share one Valkey, and a collaboration server that cannot subscribe at start does not open its port, and its health check does not answer, until it can. A notice that is lost, because Valkey was away for a moment, leaves a connection open until the re-check closes it, within 60 seconds (FR-ED-41).

**The Valkey user of the collaboration server must be allowed to subscribe to that channel, and the user of the web application to publish on it.** A managed Valkey with access control lists refuses a channel that the user's list does not name. A collaboration server that is refused prints one line on stderr, `collab events: not subscribed (ReplyError NOPERM)`, with the code word of Valkey's reply (`NOAUTH` where the password is missing or wrong), and asks again after 1 second, then after twice as long each time, and at least every 30 seconds. It prints no further line while the fault stays the same, and `collab events: subscribed again` once it is subscribed. Until then, at start, its port stays closed and it does not exit: a port that never opens, with that one line, is this fault.

**The health check of the collaboration server shows that the process is up, listening, and subscribed to that channel, and nothing else.** `GET /collab/health` answers 200 with an empty body while the process is subscribed, and 503 with an empty body and `Cache-Control: no-store` from the moment it loses its connection to Valkey for the channel until it is subscribed again (the owner's decision of 8 October 2026, which amends choice C20 of the plan for this one case; NFR-SE-05 (c)). It checks no other dependency: not the database, and not whether Valkey answers a command. The check changes only what it answers. A server that answers 503 still admits handshakes for as long as it can reach Valkey for the limits, keeps the connections it holds, and does not hear of a deleted document until it is subscribed again; the two lines above, on stderr, say why. The health check of the web application is unchanged, and checks no dependency.

A notice is never obeyed for what it says. Anything that can reach Valkey can publish one, so the collaboration server closes the connections to a document only where the document's row says it is deleted, or is gone, and closes or switches a connection for a removal, a role, or a session only where the rows say so: a notice that the rows do not bear out changes nothing. A message names a kind and identifiers of the application, and no title, name, address, or token (NFR-SE-19). The Valkey of the application is reachable by the two processes alone.

## Deleted documents

A deleted document is kept for `DELETED_DOCUMENT_RETENTION_DAYS`, 30 where unset, at least 1 and at most 3650, and is then deleted permanently, with its state, by a timer in the web application that runs at start and each hour (FR-ED-36, NFR-RE-15). Any number of instances may run it: each document is claimed by one of them.

**Lowering `DELETED_DOCUMENT_RETENTION_DAYS` applies to the documents that are already deleted.** The end of a retention is not stored with the document: each run works it out from the moment of the deletion and the setting as it then is. At the first run after the setting is lowered, every document deleted longer ago than the new value is deleted permanently, although its Owner was shown the date the old value gave. Raising it gives every deleted document the longer time.

**The instances agree on the setting and on the time.** Each instance judges a retention, and the age of another instance's unfinished claim, by its own clock and its own setting, against times that the other instances wrote. Every instance of the web application is given the same `DELETED_DOCUMENT_RETENTION_DAYS`, and their clocks are kept together, as a time service keeps them: an instance whose clock runs ahead deletes that much early.

The lines of this work, on stderr, each name the document by its identifier and never by its title (NFR-SE-19):

- `permanent deletion: document <id> kept (…)`: the document could not be deleted in that run, and is tried again in the next. In the brackets, `Istorico did not erase`, or the class and code of a fault.
- `collab events: document-deleted not published for document <id> (…)`: the document is deleted, and the collaboration servers were not told. Its open connections stay open until their browsers close them.
- `collab events: document-deleted not handled for document <id> (…)` and `collab: document <id> not read for a notice (…)`: a collaboration server was told and could not act, or could not read the row. In the second case it closes the connections to the document as unavailable, and each browser connects again.
- `collab events: collaborator-changed not published for document <id> (…)`, `collab events: permission-set-changed not published for document <id> (…)` and `collab events: session-ended not published for user <id> (…)`: a removal, a leave, a change of role, a change of a permission set, or the end of a session was committed, and the collaboration servers were not told. The change stands, and the connections it concerns are closed or switched by the re-check, within 60 seconds and not the 5 of FR-ED-40. `collab: re-check not read for sessions (…)` and `collab: re-check not read for access (…)` are the readings of a look or of the re-check that failed, and the connections they were for were closed as unavailable. The lines name the identifiers of the application and never a name or an address.
- `collab: last store of document <id> failed (…)`: a collaboration server could not store what it had received for the document before closing its connections. They are closed all the same. What is lost is what that server had received since its last store, at most the 2 or 10 seconds of `COLLAB_STORE_DELAY_MS` and `COLLAB_STORE_MAX_MS`; the state stored before stays, and is what a restore returns.

## Deleted accounts

An account is deleted by its user (FR-AU-58) and by no other route; the identity library's endpoint for deleting a user is off. When the user confirms, the application records the deletion and from that moment the account has no session, signs in nowhere, and its connections to the collaboration server are closed (within 5 seconds by the notice on the channel, and within 60 by the re-check, which reads the rows). The steps that follow are carried out by a timer in the web application that runs at start, each hour, and once after the confirmation: Istorico (none in α 0.1.0), the feedback intake (skipped while `FEEDBACK_INTAKE_ENABLED` is off, which it is in α 0.1.0), the sessions and the credentials, and the personal fields of the row (docs/plan/slice-22.md). A step that fails is repeated by the next run. α 0.1.0 runs one instance of the web application (register D169, D176), and that is all that has been shown: a second instance running the timer is written for (each deletion is claimed by one of them, every write of a step names its claim, and a claim an hour old is taken over) and is shown in the release that first runs one (Q42). **The claim relies on the instances' clocks agreeing**, as the claim of the permanent deletion of a document does (the section above): an instance whose clock is more than an hour ahead of another's takes over a claim that is still being worked, and the writes of the run that lost it are refused, but a call that run had already made (to Istorico, once linked, or to the feedback intake) is made twice. Both calls are idempotent on the request they carry.

The clearing of an account's documents (FR-AU-91; docs/plan/slice-23.md) is recorded when the user confirms and carried out by a timer in the web application, `clearing-deletion`, that runs at start, each hour, and once after the confirmation: a document that is not shared is deleted at once, and a shared one on the day, `CLEARING_NOTICE_DAYS` (7 where unset, at least 1) after the confirmation, by the first run after it (up to an hour late). **The day is stored with the clearing and the document when it is confirmed**: lowering the setting later does not bring a day nearer. Each document is claimed by its own `deletionClaimedAt`, as the permanent deletion of a document is, so any number of instances may run it, and a claim an hour old is taken over; it relies on the instances' clocks agreeing in the same way (an instance whose clock runs ahead deletes a shared document that much early, before its collaborators' notice has run). The email of the notice is handed over once, under the clearing's own claim, with a timer (`clearing-email`) for what a stopped process left; it names no document and no title. The notification of the deletion holds the document's title for 30 days, and nowhere else.

**The one-month limit (NFR-DP-06) is watched by one line.** A run that finds a confirmed deletion still open a calendar month after its confirmation writes `account deletion: [n] confirmed deletions are open past the one-month limit (NFR-DP-06)` on stderr, with the number and nothing else. What raises an alarm on it is the owner's to set up with the rest of the monitoring (docs/plan/slice-22.md, S22-9). Each step that fails writes `account deletion [identifier]: step [name] not done ([class])`, never a name or an address.

**`FEEDBACK_INTAKE_ENABLED` stays off until the release that adds the Feedback Widget.** Turned on before then, every deletion stops at the step that instructs the intake and is repeated each hour, because the client of that request is built with the widget.

## The draft export (FR-EX-36)

The Markdown draft export is the one response of the application that is long and is written as it is sent: a ZIP archive, streamed from the store of the images, with no copy kept (`src/lib/export/`; `docs/plan/slice-21.md`). Four things are the deployment's.

13. **The proxy does not keep the response to give it on.** A proxy that reads a response from the process at the speed of the process and gives it to the client at the speed of the client holds the whole archive, up to the 100 MB of images and the text, in memory or in a file of its own, which the application's rule of keeping no copy cannot reach; and the idle period of the export then measures the proxy and not the client. The response carries `X-Accel-Buffering: no`, which nginx reads; any other proxy is set not to buffer the responses of `POST /api/documents/<id>/export/draft`.
14. **The proxy closes a connection to which it can send nothing for as long as the export's idle period** (`EXPORT_IDLE_SECONDS`, 30 where unset; nginx `send_timeout`). The application ends an export that makes no progress in that time: it releases the lock of the user, stops the read of the store and ends the stream. Where the cause is the store, or a fault, Next.js 16.4.3 then destroys the connection, so that the browser reports a failed download. Where the cause is a client that is connected and has stopped reading, it does not: the framework's writer is waiting for the socket to drain, and an abort waits behind that wait (measured, `tests/e2e/export.spec.ts`: the lock was free after the period, the connection was still open eight seconds later, and it ended as an aborted download when the client read on). The connection holds one chunk of the response (16 KiB) and nothing else of the export's until the client or the proxy closes it (register row S21-9). The slowest reader the idle period keeps alive takes one chunk of 16 KiB in the period (about 0.55 KiB a second), and each export under way holds one of the 50 sockets that the store's client shares with every other read and write of images in the process (register row S21-7).
15. **The store's credential is the one the application already has**: the export reads the objects with `GetObject`, which the links of images need as well (`src/lib/images/s3-storage.ts`); it adds no permission.
16. **`EXPORT_IDLE_SECONDS`** (30) **and `EXPORT_NAME_MAX_CHARS`** (100) are the initial values of FR-EX-36, and **`RATE_LIMIT_EXPORTS_PER_USER`** (`10/3600`) that of NFR-SE-07. The lock of one export at a time is a key in Valkey that lives as long as twice the idle period without being renewed, so that a process that dies holding one releases it within a minute.

## Settings

A process refuses to start without `FOUNDING_TEAM_EMAILS`, `APP_ORIGIN`, `DATABASE_URL`, `VALKEY_URL`, and `AUTH_SECRET`, and, away from a development machine, without `EMAIL_TRANSPORT` (`sink` or `brevo`), a `TRUSTED_PROXY_COUNT` of 1 or more, and either `EMAIL_SINK_DIRECTORY` with the sink, or, for the web application alone, `BREVO_API_KEY` and `EMAIL_FROM` with Brevo (see Email, below). `.env.example` describes each. No variable whose name begins `BETTER_AUTH_` may be set: the identity library reads several of its own, which would change its configuration, and each of the two processes refuses to start where one is present. A variable whose name begins `RATE_LIMIT_` and names no limit stops a process in the same way, as does a period or a length that is 0 or out of order.

An entry of `FOUNDING_TEAM_EMAILS` that is not an email address an account can have stops a process too (the owner's decision of 9 October 2026): an entry with no domain, or with a domain written in full-width or other compatibility letters, or with a label that begins or ends with a hyphen. Such an entry would match no account, and the account it was meant for would not be required to use two-factor authentication. The message gives the position of the entry in the list and never the entry.

`EMAIL_SINK_DIRECTORY` names the directory the email sink writes to, with `EMAIL_TRANSPORT=sink`. Each file in it holds an address and may hold a single-use link, so a deployment says where they go: only on a development machine is a directory under the working directory used where the setting is absent. With `brevo` the setting is not read.

`TWO_FACTOR_STEP_SECONDS` is how long the second step of a sign-in stays open after the password, and how long the secret of an enrolment waits for its first code: 600, the 10 minutes of FR-AU-83, where the setting is absent. `TWO_FACTOR_WRONG_CODES` is the number of wrong codes at which either is over and begins again with the password: 5 where the setting is absent (NFR-SE-07). Each is a whole number, 1 or more, and anything else stops a process.

`SIGN_IN_LOCK_SECONDS` is how long the twentieth failed sign-in for an email address locks its account, and how long the sign-in link in the email of the lock is valid: 3600, the 1 hour of FR-AU-81, where the setting is absent. The twenty and the hour they are counted in are the limit `RATE_LIMIT_FAILED_SIGN_IN_PER_EMAIL`. The email of the lock states all three as they are set. A process refuses to start where `SIGN_IN_LOCK_SECONDS` is less than the seconds of that limit: the failures that caused a lock would still be counted when it ended, and each single failure after it would lock the account again and send its email. The lock is the column `User.lockedUntil`, so it holds on every instance; a sign-in reads it once, and is refused where the database does not answer.

Three ceilings of the lock and its link are accepted as they are. The count of the five codes that a sign-in link is given in all is kept in Valkey alone, so a link whose count Valkey loses within the hour of the lock is given five more. Where Valkey fails while the counts are cleared after a sign-in by the link, the sign-in stands and the count for the address stays at its number, so until those failures leave their hour the next lock takes one failure and not twenty. And the lock runs on the clock of the application's instance while the counts run on Valkey's: this matters only with more than one instance and clocks that differ, where a lock ends on one instance that much before another. Should it come to matter, the three conditional statements that compare a time (`src/lib/auth/sign-in-lock.ts`) take the database's `now()` instead.

The database client gives up on a connection after 5 seconds, the server ends a statement after 5 seconds, and the client stops waiting for an answer after 5 seconds (`src/lib/db.ts`; NFR-SE-06). A connection to Valkey and a command sent to it are given 5 seconds each (`src/lib/valkey.ts`). A request that meets either fault is refused and never passed on.

### The object store of the images (FR-ED-08, NFR-SE-18)

`IMAGE_STORAGE_ENDPOINT` (`https://fra1.digitaloceanspaces.com` for Spaces in FRA1), `IMAGE_STORAGE_BUCKET`, `IMAGE_STORAGE_ACCESS_KEY_ID` and `IMAGE_STORAGE_SECRET_ACCESS_KEY` are given together or not at all: with some and not all a process refuses to start, naming the missing and never a value. With none, no image can be uploaded or shown (the routes answer 503), the policy of a page names no origin beside its own, and a deployment away from localhost writes one line at start saying so. **A deployment of the release sets all four.** The secret differs from `AUTH_SECRET` and `ADMISSION_SECRET`, and is held in the environment of the web application alone: the collaboration server reads the settings but never the store. `IMAGE_LINK_SECONDS` (300, at most 3600), `IMAGE_UNREFERENCED_DAYS` (30) and `IMAGE_DOCUMENT_MEGABYTES` (100) are the initial values of NFR-SE-18.

What the owner provisions, and the application cannot check: the bucket admits **no public read and no listing** (the credential the application holds lists nothing and the code never lists; `tests/integration/image-store.test.ts` shows it against a store of the protocol); it is in FRA1; its objects are versioned or copied each day to a second bucket in FRA1, which NFR-RE-10 asks and the owner records; and the response of the store to a link carries `Content-Type` and `Content-Disposition: inline` as the link was signed for. **`X-Content-Type-Options: nosniff` on that response is the store's to send, and nothing of the application's can add it:** the four types an image is stored as are never a type a browser runs, and the link signs the type, so the header is a second belt that Spaces may or may not put on; check it once when the bucket exists. The request of an upload passes the proxy of the application: `next.config.ts` sets `proxyClientMaxBodySize` to 21 MB so that an image of up to 20 MB arrives whole; a reverse proxy in front must let a body of that size through, and the timer `image-deletion` (hourly) removes an image 30 days after it left its document.

Four more things the owner sets or checks, from the review of pull request 52. **The Spaces key is scoped to this bucket and no other**: the key of a Spaces access key can be limited to one bucket with read, write and delete on it, and the application needs nothing beyond `PutObject`, `GetObject` (for the links) and `DeleteObject`; a key of the whole account would put every bucket of the account behind a fault of this application. **Where versioning is on, a lifecycle rule expires the old versions** (for example 30 days after they stopped being current): a deletion of the application removes an object from view and keeps its earlier version, and NFR-SE-18 says "deleted from storage". The daily copy to the second bucket (NFR-RE-10) holds an object deleted here until the copy's own retention ends, which the owner records beside the 30 days. **Only the route of an upload needs a body of 21 MB**: `proxyClientMaxBodySize` is a setting of the whole proxy of Next.js, so it lets 21 MB reach every path that the proxy runs on, and it is the bound each route sets on what it reads that keeps the others small; a reverse proxy in front may limit every other path far lower, and must let 21 MB through to `POST /api/documents/{id}/images`. **The list of what each document held at its last store is kept in the memory of the collaboration server** (`src/lib/images/references.ts`, at most 1000 documents), which is why it is one instance only (above): a second instance, or a restore of the database without a restart, would hold a list that no longer matches the rows, and an image that was put back in a document could be deleted after the 30 days. NFR-SC-04 removes the list or moves it to Valkey.

Changing `AUTH_SECRET` ends every session and forgets every count of NFR-SE-07, since the counters are stored under digests keyed by it. The procedure for rotating each secret is [secret-rotation.md](secret-rotation.md) (NFR-SE-17 (e)): changing `AUTH_SECRET` alone also makes every second factor unreadable, and the procedure re-seals them first. The copy of the backups outside DigitalOcean is [backup.md](backup.md), and the procedures that show the release criteria are in `docs/procedures/`.

## Before a deployment that holds accounts created under an earlier rule

A one-off check, which the owner decided on 9 October 2026. An address is stored in its one spelling and under the one rule of an address (`src/lib/field-text.ts`; FR-AU-02): composed, in lower case, with one sigma, and with a domain that is plain or is a Unicode label that normalisation leaves as it is, and with no label in punycode (a label that begins `xn--`, in any case and in any place of the domain; the owner's decision of 12 October 2026, whose register row is pending). An account created before that rule, or before a later change to it, may hold an address that the rule now spells otherwise or refuses. Such an account may be one that no sign-in finds, one that the list of the founding team does not match, or one beside which the same person is given a second account. The same holds for an open invitation (FR-AU-89): one still pending and not past its expiry, which was written under an earlier rule, is for an address that the rule now refuses, and the person it reached meets a refusal nobody foresaw.

1. **Before the first deployment to a database that holds accounts created under an earlier spelling or rule of an address, run the check, with the settings of that deployment:** `node --env-file=<the file of settings> scripts/check-addresses.ts`. It reads the identifier and the address of every account and of every open invitation, and changes nothing. It prints one line, `address check: <n> of <m> accounts hold an address that is not in its one spelling or that the rule of an address refuses`, and then the identifier of each such account on a line of its own; and one line, `address check: <n> of <m> open invitations are for an address that is not in its one spelling or that the rule of an address refuses`, and then the identifier of each such invitation on a line of its own. An invitation is open by the definition of the admission code: stored as pending, and not past its expiry. It never prints an address (NFR-SE-19). It exits with 0 where there is no such account and no such invitation, with 1 where there is one or more of either, and with 2 where it could not run, in which case the line says `address check: not run`.
2. **Where it names an account or an invitation, the deployment waits, and the identifiers are reported to the owner.** No row is migrated silently, by the check or by hand. The owner decides for each account what becomes of it: an address rewritten to its one spelling could be the address of another account, and a person signs in with the address as they know it. For an invitation the owner decides whether it is revoked and sent again to an address the rule accepts.
3. **The check is run again after whatever the owner decides is done, and the deployment goes ahead when it exits with 0.** The result is recorded with the deployment.

## Email

There are two senders, chosen by `EMAIL_TRANSPORT` (register D206, D262). **`sink`** writes each message to a file and sends nothing: a deployment that sets it sends no invitation, no reset link, and no notice. The sink is still allowed away from a development machine; the owner's answer p65-1 would refuse it on a server, and that refusal is not built yet. **`brevo`** sends each message through Brevo's API.

`BREVO_API_KEY` and `EMAIL_FROM` belong to the web application alone. The collaboration server sends no email, so it neither holds nor checks them; it needs `EMAIL_TRANSPORT=brevo` only, which it refuses to start without away from a development machine. The key is the key alone, with no space or line break at its end, and differs from `AUTH_SECRET`, `ADMISSION_SECRET` and the secret of the image store: the process refuses to start otherwise, and no message of a refused setting repeats the key. `EMAIL_FROM` is a name of at most 70 characters and an address on a domain that is not localhost and not an IP address, in the form `Ekdotico <no-reply@ekdoti.co>`.

**Switching Brevo on is the owner's step, and nothing in the repository does it.** The order, so that no real email goes before it should:

1. In the Brevo account, make the settings that D262 makes conditions: email previews off, a retention rule (30 days if the settings offer it), tracking anonymised, the written request to turn click tracking off for the account, Brevo's AI features not used, and a dated copy of the terms kept. Authenticate the domain of the sender, and make a key for this application alone, so that it can be rotated ([secret-rotation.md](secret-rotation.md)). Check whether the account restricts the addresses a key may be used from, and look at its block list of addresses (see the first send, below).
2. **Switch on with nothing due.** The timers run once as the process starts (NFR-RE-15). A reminder of an invitation, an offer of ownership or a notice of a clearing that is due then is marked before it is sent, so if the first send fails it is not sent again. Do it on a deployment with no invitation near its expiry, no offer open and no clearing awaiting its notice, which for the first deployment means before the first user. Set `EMAIL_TRANSPORT=brevo` in both processes, and `BREVO_API_KEY` and `EMAIL_FROM` in the web application only, and restart.
3. **Send one test email to an address of the owner's own**, and compare the link in it with what the application builds. By default ask for a password reset for that address on the reset page (the address must have an account): the link must begin with `APP_ORIGIN` followed by `/reset-password/`, with the host and the path exactly those, and not a host of Brevo's or a long address that redirects. Only for an address that has no account, create an admission invitation with `pnpm admission create` (an address that has one answers 409), whose link begins `APP_ORIGIN` and `/sign-up/`. That is how Q74 is tested: if Brevo rewrote the link, and click tracking is not off for the account, send no email to a test user.
4. **What the first send also shows**, and is written in the record of the switching on:
   - Whether Brevo takes `textContent` alone. Its reference calls `htmlContent` required when there is no template. If it refuses the message (the log says `MessageRefused MISSING` or `INVALID`), do **not** add HTML to get past it: it comes back to the owner as a question.
   - The status that a sender it does not know, and an account with no credits, draw. The log prints `Error 400_CREDITS`, `400_DOMAIN`, `400_KEY` and the like for the codes it lists, `Error 400` for any other, and the bare status for the rest. Note the status against the cause in the record.
   - A display name that holds braces, such as `{{ x }}`, in a document invitation sent from an account of the owner's to another: whether Brevo draws a refusal or expands it.
   - Whether the address reached it: 201 is acceptance and not delivery. Brevo keeps a list of addresses it will not send to after a hard bounce, and may accept and then drop; look at it in the account.

### What a fault looks like in the log

NFR-SE-19: a line names the fault by its class and a short code or status, and the kind of email, and never an address, a subject, a body, the key, or what Brevo answered. There are two groups.

**Through `handOver`: the email of an account** (reset, confirmation of an address, the notice of a lock, the notices of a password, an address, two-factor authentication and recovery codes, and the admission invitation). A fault is tried again for up to 10 minutes (FR-AU-87), and the lines are:

- `email: hand-over failed, trying again (Error 429) (password reset)`, once, at the first failure. The code is the status, `Timeout`, the code of the network fault (`ECONNREFUSED`, `UND_ERR_CONNECT_TIMEOUT`, `EAI_AGAIN`), or `400_CREDITS` and its kind for a 400 whose code is on the list.
- `email: a message was not handed over within 10 minutes (<kind>)`: lost. The person can ask again.
- `email: a message was not handed over, the process is stopping (<kind>)`: the process was stopped (SIGTERM) while it was waiting, and gave up; the retries do not outlast a restart.
- `email: a message was refused and not handed over (MessageRefused INVALID) (<kind>)`: Brevo refused the message itself (`invalid_parameter`, `missing_parameter`, `out_of_range`), and it is not tried again.
- `email: a message was seen by the service already, not sent again (MessageSentAlready DUPLICATE) (<kind>)`: Brevo said `duplicate_request`, so the message very likely arrived.

**Sent once, not tried again: the email of a document** (an invitation and its reminder, an offer of ownership, the notice of a clearing, the notice of a transfer of an account). FR-ED-21 marks the row before the email is handed over and never hands over a second for a marked row, so a fault, and a timeout above all, where the outcome is unknown, is one line and no more: `invitation <id>: not delivered (Error 401)`, `invitation <id>: reminder not delivered (…)`, `ownership offer <id>: email not delivered (…)`, `clearing <id>: an email was not delivered (…)`. The email is lost, and the Owner recovers it by sending the invitation or the offer again, which is a new one (FR-ED-37).

What the statuses mean, as far as Brevo's reference states them: it documents 400 alone, with a code. A 401 is a key that Brevo does not accept (revoked, mistyped, or used from an address the account does not authorise); a 402 or a 403 is an account that is not allowed to send (credits, a permission, a sender not authorised). The reference does not state them, and the first occurrence is what shows. All three are faults of the account and not of a message, and are tried again by the first group until they are mended; for the second group the email is lost until the Owner sends again. Mend the account, then look for the first line of the first group in the log.
